[T3.1b S5, the D222 reranker-lane verdict from measured inputs] **The tier-2 reranker is off for `robust_pr`; `core` keeps it.** `robust_pr` is then documented as first-stage robustness (D222, mechanism D271: `rerank.on_retrieve: false`).

**Measurement** (2026-11-17, `experiments/model_selection/rerank_bench.py`, `results/rerank_latency.csv`):
- `bge-reranker-v2-m3` on the VM CPU (`rerank-cpu`, `RERANK_CPUS` default 8);
- 10 passages per query in one batched request, cut to 256 tokens, 100 German queries.

| Concurrency | Wall time per query | Per request |
| --- | --- | --- |
| 1 | **3.93 s** | p50 3.89 s, p95 4.47 s |
| 4 | **11.75 s** | p50 46.8 s |

The phase-1 assumption was 1.2 s/query.

**Lane.**
- PR run: 790 queries (smoke 50, core 300, `robust_pr` 440) × 3.93 s = **51.8 min**, above the 20-minute limit.
- `robust_pr` alone: 440 × 3.93 s = **28.8 min**, still above it.

So the reranker stays on only where answers are generated (`/v1/query`).

**Ways back** (each an owner decision, then a new measurement with `rerank_bench.py`):
1. **More CPUs for `rerank-cpu`.** This is the first suspect: concurrency 4 was slower per query than concurrency 1, so the service is CPU-bound at its default of 8 CPUs on a 160-vCPU VM.
2. Tuning the intra-op threads.
3. A lower `rerank.top_n`.

**Not changed here:** the gated configs. `rerank.on_retrieve` is still `true` in `apps/rag-demo/configs/rag.gpu.yaml` and its one-switch copies. The follow-up changes them together (`rag.gpu.yaml`, `configs/bugs/gpu/*.yaml`, `configs/cause/*.yaml`) and re-measures nothing.
