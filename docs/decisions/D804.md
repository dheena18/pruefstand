[T5.2b, tier-1 selection, interface change] `Runner` gains the keyword-only `judge_scope: JudgeScope(case_ids, canaries)`. With `budget.max_requests_per_run` set (tier 1: 10 / 60) the pipeline chooses the judged cases with `metrics.judged.routing.select_judged_cases`: cases ordered by `stable_hash(dataset_version, case id)` (so baseline and PR judge the same ids), taken while the planned calls (one per judged metric that can apply) fit in `cap - 1` (the runner reserves two requests per call, one for the repair; the cap is never exceeded), probes and cases with a registered canary in question or reference dropped before counting. The others get `not_applicable` / `judge_not_selected`. A case whose answer or chunks hold a registered canary gets `canary_in_input` (the external-provider data guard would otherwise count a `PolicyViolation` as a judge error). With a request cap the judge calls are serialised (an `asyncio.Lock` in `JudgeStage`) so reservations never race and the result is reproducible. `judged_cases` counts only cases where a judge decided (not a `not_applicable` value, not a refusal the phrase list decided)
