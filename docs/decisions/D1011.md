[T5.2c, prompt cache false positives of (c)] Ollama's prompt cache lowers `prompt_eval_count` by the cached prefix (D343). The shared fixed prefix of the four judge prompts (system rubric plus the user lead-in before the first nonce block; the blocks start with a per-input nonce, so nothing after them is shared) measures 879 (faithfulness), 1 128 (answer_correctness), 570 (perturbation_consistency) and 552 (refusal_judged) tokens with the gemma3 tokenizer (`test_gemma_tokenizer.py` pins the range 500 to 1 200). Sign (c) therefore (1) compares with `exact - fixed_prefix`, the lowest honest report after a full prefix hit, and (2) only looks at prompts of at least 0.9 x `num_ctx - num_predict` (a cut needs a prompt that nearly fills the window: 10 810 tokens fit, 14 000 were cut), so a short prompt that a cache hit makes tiny is never flagged. Residual risk, accepted: a byte-identical prompt of 10 700 tokens or more, repeated with the pruefstand LLM cache off, whose repeat Ollama reports far below 0.8 x its length, reads as cut. `num_ctx` is sent with every judge request: `llm/backends/kwargs.py::_ollama_kwargs` writes the catalogue value over whatever the caller asked, pinned for a plain call, for the JSON-repair retry and for every `max_tokens` (including the doubled repair budget) by `test_judge_num_ctx.py`; a fallback judge goes through the same `completion_kwargs` with its own catalogue entry
