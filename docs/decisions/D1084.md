[T6.2a, review of #171] **Consecutive-timeout stop.** With tier-1 timeouts at 180 s and no retry (D1082), 20 cases at concurrency 2 against a hung target would take 30 min of target time, the `live` job's `timeout-minutes`. New `RunnerConfig.max_consecutive_timeouts: int | None` (default `None` = off, `>= 1`): after that many target timeouts in a row (completion order; a success resets it) the runner stops calling the target. Every later case is still recorded, as an error `"not run: stopped after N consecutive timeouts (runner.max_consecutive_timeouts)"` with `attempt == 0` (worst value, `error_rate` 1 for it), and counted in `RunManifest.counts["aborted_after_timeouts"]` (also in `error`); nothing is dropped and the gate is unchanged, so a hung target ends in a clean `error_rate` FAIL in about 10 min. Values: tier-1 configs (`examples/live/*.yaml`) 3; the root tier-2 `pruefstand.yaml` 16 (2 × its concurrency 8: one transient upstream stall that times out a whole wave of 8 must not turn every remaining case into an error). `runner.retry.is_timeout` now matches only the two texts this package writes, anchored (`"timeout after <n> s"`, `"<METHOD> <path>: timed out after <n>s"`), so a target-controlled body such as `"HTTP 504: upstream timed out after 30s"` is not counted as a timeout. `docs/engineering/ci-cd.md` §1.1a, interfaces §8 and the `RunManifest` docstring list the new field and counts. Which cases end up `not run` depends on the completion order of concurrent cases, so the aborted set is not reproducible between runs (only the stop itself is). `aborted_after_timeouts` is shown in the PR comment next to the Timeouts line ("Not run: N cases after consecutive timeouts …") and in the HTML report's counts; report only, no gate change.
