[T6.2a, llm-proxy per attempt] Every gate attempt (dispatch, main promotion, nightly) brings up the `llm-proxy` service of `compose.executor.yml` itself before it starts the candidate and removes it in `finally` (`docker compose -f compose.executor.yml up -d --wait llm-proxy` / `rm -sf llm-proxy`), so the owner never starts it by hand. `LLM_PROXY_POLICY` is written by the orchestrator: `{tag: catalogue fields}` for exactly the generator and embedding models that main's `apps/rag-demo/configs/rag.gpu.yaml` names, read from `infra/gpu/models.yaml` of the pinned main worktree; a judge, an unknown model or an entry without an integer `num_ctx` is refused (`proxy_policy` infra error) before anything starts, and the proxy's own parser accepts the result (test). A proxy that does not come up healthy is the infra error `proxy_down` (retried once like any infra error). Limitation: a PR whose `rag.gpu.yaml` names other catalogue models is still served main's models through the proxy; wiring `plan()` (D1067) into the attempt is a follow-up. Review #258: compose interpolates the whole file for every command, so the teardown runs with the same env as `up` (including `LLM_PROXY_POLICY`; checked against the real compose CLI); its exit is checked and a failed removal is the infra error `proxy_cleanup` when the attempt itself succeeded (never hiding the attempt's own error). The plan() wiring for PRs that name other catalogue models is follow-up T6.2a-F2.
