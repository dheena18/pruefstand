[T3.6, timeouts and retries] The generator serialises requests (about 14.4 tok/s aggregate, TTFT p95 32 s at 4 and 70 s at 8 streams, `experiments/model_selection/REPORT.md`), so the tier-2 read timeout is the catalogue entry's `request_timeout_s` when present, else 300 s (connect 10 s); a read timeout is **not** retried (it would only add queue load) and ends in `GenerationError` → API 503. Only HTTP 503 (Ollama queue full / model loading) and connection errors are retried, twice (1 s, 3 s); 502/504 are not, because a proxy that already forwarded upstream would re-run the same generation. **Gate requirement (T6.2a, tier-2 gate config; T3.7 uses it too):** the runner `timeout_s` must exceed 300 s or `concurrency` must be at most 4, and the runner must not retry a read timeout; the defaults (`timeout_s` 60, `max_retries` 3, `concurrency` 8) would time out first (TTFT p95 70 s plus about 140 s decode at c=8) and rag-demo would keep the original request queued in Ollama, up to 4 duplicate generations and a higher `error_rate`. Cancelling the upstream call on client disconnect is a follow-up (not done here) Generator errors never contain the bearer key, a response body or a stack trace. Sampling options stay the config's (`generation.*` inside the catalogue `option_bounds`); `rag.gpu.yaml` keeps `max_tokens` 256 (catalogue bound 512) which is also what bounds the PR time budget (the budget assumed about 200 output tokens). `keep_alive` is never sent, `think: false` always (part of `config_hash`)
