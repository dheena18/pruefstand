[T1.7a, gate.policy hardening] The baseline-error check of a gated slice (`gate/_baseline.py`) counts only the baseline's applicable cases (`ok` or `error`) in the 20 % denominator, never `not_applicable` ones; baseline `error` values that leave fewer than `min_clusters` of the slice's applicable clusters are a `GateInputError` (slice and `overall`; for a metric the pipeline did not mark informational, also when they would push `overall` below 30 applicable clusters, which used to demote the metric to `applicable_clusters<30` unseen). `ScoredCase` rejects a metric listed twice (the gate read the first entry, `_validate` all of them). The cap boundary is pinned with 12 of 60 (passes) and 13 of 60 (raises). Because that raise would hit every PR against such a baseline (a tier-2 baseline may carry up to 5 % judge errors, e.g. 2 errors on single-case clusters of a 31-cluster slice), `pruefstand baseline promote` runs the same check first (`gate.baseline_run.check_baseline_run`, called from `cli/baseline.py`, because `store` sits below `gate`) and refuses the run; the gate-side raise stays as a backstop. Operator action: re-run the baseline (or promote a run with fewer judge errors); the message says so. The T1.10 `directions` cross-check against `MetricRegistry` and the hard-fail `not_applicable` reasons for robust_pr / retrieve mode stay with T1.10 (D360h), no new work here (source: T1.7 reviews)
