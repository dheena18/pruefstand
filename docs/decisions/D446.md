[T6.1] Cache trust domains: `PRUEFSTAND_CACHE_MODE` is `overlay` (default; main's cache opened read-only under `PRUEFSTAND_CACHE_DIR` or `$PRUEFSTAND_HOME/cache`, writes into a per-job temp directory deleted afterwards, also on failure) or `shared` (one writable cache for main and nightly); anything else is a `ConfigError`. `pipeline/cache.target_cache()` wires it into `run_eval`; a cache that cannot be opened is "no cache" (an unreadable shared cache in overlay mode still gives the PR its own overlay). **Cache identity (review of PR 41):** a PR image is untrusted code and the cache key rests on what the target reports about itself, so (a) a PR job reads main's cache only when the executor sets `PRUEFSTAND_TRUSTED_TARGET_ID` (the image digest it pulled); that id is hashed into `target_fingerprint` and the cache key, the reported git sha/digest can only add to it; without it the PR gets its own empty overlay, never main's answers; (b) a target that reports git sha `unknown`/empty and no image digest (or no `/v1/info`) is opaque: no cache at all, neither read nor written; (c) `counts.cached_from_base` records answers served from main's cache; the gate refuses a candidate that has it for all its cases (`GateInputError`: the candidate never ran), downgrades a PASS with some to WARN, and the PR comment shows "N of M answers served from cache (baseline overlay)" `build_cache(mode, shared, overlay, namespace)` also serves namespace `llm`, but no `LLMClient` exists in `run_eval` yet (judges arrive with T5.2a/b): that wiring is a follow-up of T5.1/T5.2b
