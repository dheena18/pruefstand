[T3.1d, round-3 review minors] `pruefstand-lock` takes the lock in-process and `exec`s the command: a small fixed python3 program (`python3 -I`: `flock(2)` with an alarm for the timeout, `0` = do not wait, then `os.execvp`; SIGPIPE/SIGXFSZ/SIGALRM reset because an ignored signal survives `exec`). The command is the lock holder, so a TERM/INT/HUP sent to the pid of `pruefstand-lock` reaches it (no orphan that keeps the lock), no helper process sits between caller and command, `/proc/locks` names the command's pid (the `pruefstand-cluster` ancestor proof is unchanged), `-c` and every other argument belong to the command (no `flock(1)` option parsing), and exit codes are the command's own: 75 is printed as `gpu.lock busy` only when this wrapper timed out, a missing command exits 127 (126 if it cannot be executed) before waiting for the lock. The interpreter is `/usr/bin/python3` (not a PATH lookup; `PRUEFSTAND_LOCK_PYTHON` is a test seam), missing -> exit 78; `setup-users.sh` checks it first, before it plans or changes anything. The command's environment is left as the caller had it: python's PEP 538 coercion `LC_CTYPE=C.UTF-8` is undone (bash passes the original LC_CTYPE, set or unset, as arguments), an ignored SIGPIPE/SIGXFSZ stays ignored (`trap -p`), SIGINT while waiting ends the process quietly (130/signal), `GPU_LOCK_TIMEOUT_S` over 9 digits is exit 64. A command that exists but cannot be executed exits 126 (a missing one 127). This supersedes the D416 sentence that `pruefstand-lock` runs `flock -w N -E 75 <lock> <cmd>`. Chosen over a trap-forwarding bash wrapper because that needs a separate process group, which breaks terminal input (SIGTTIN) for interactive commands.
