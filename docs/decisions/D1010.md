[T5.2c, exact judge-input count; owner request] A judge input counts as cut when ANY holds: (a) `reported >= num_ctx - num_predict`; (b) `reported` in the measured band `[num_ctx / 2, num_ctx / 2 + 16]` (D962, unchanged); (c) NEW: `reported < 0.8 x (exact - fixed_prefix)` for a prompt whose exact count is at least 0.9 x the window (`judges/exact_tokens.is_cut`). `exact` is the token count of the joined messages with the judge's own `tokenizer.json` plus `TEMPLATE_TOKENS = 10`, calibrated on the gemma3 measurements of D962 (910 / 3 610 / 7 210 / 10 810 reported tokens for 500 / 2 000 / 4 000 / 6 000 words of 1.8 tokens: the overhead is exactly 10 each time; the template string itself costs 9 with the real tokenizer, `test_gemma_tokenizer.py`). Why the estimate cannot do this: it over-counts German prose about 2.2x on purpose, so `0.8 x estimate` would flag almost every normal call. A cut judge input stays `JudgeInputTruncated` (candidate-side, worst-filled, D813-D815): never a pass. New dependency `tokenizers>=0.21` in `packages/pruefstand/pyproject.toml` (reason: exact judge-input count for gate correctness; it is already in the lock as a dependency of `litellm` and of rag-demo, so `uv.lock` gains only the edge and `pip-audit` sees no new package). The gemma3 pin is now a HF commit (`unsloth/gemma-3-12b-it@9478e665...`, same sha256 `4667f208...` as `main`). The 33 MB file is never committed: `scripts/models/fetch_judge_tokenizer.py` downloads it, verifies the sha256 and writes `$PRUEFSTAND_JUDGE_TOKENIZER_DIR/<tag>.json` (default `$PRUEFSTAND_HOME/tokenizers`); the file is hashed against the pin once per process, at first use, and `prepare_judging` loads it before the first judge call, so a mismatch is a `ConfigError` before any LLM call; sign (c) is skipped for an answer of the fallback judge (another tokenizer); an exact count at or above the window is a cut without any report. Without the file sign (c) is skipped, (a) and (b) remain, and the run records `counts["judge_exact_count_unavailable"]`, which the PR comment shows as "Judge input check: exact count unavailable". **T6.2a: the tier-2 executor and its image must run the fetch script once (the file must be present there).**
