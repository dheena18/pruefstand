[T5.2b, input cap, interface change] `JudgeLike` gains `input_cap` (property) and `prompt_tokens(task)`; `Judge` implements them (`input_cap` = catalogue `num_ctx` - 1 024 = 11 264 for `gemma3:12b`, GitHub Models `tokens_per_request` - 1 024 from `quotas.yaml`, else 8 192 - 1 024; read on first use, so building a `Judge` still needs no catalogue, D520). No tokenizer file is available offline and `tokenizers` would be a new dependency, so tokens are estimated as UTF-8 bytes / 3 (`judges/tokens.py`), which over-counts German and so truncates earlier than a real tokenizer, never later (follow-up: the catalogue `tokenizer`). `fit_context` drops the lowest-ranked `kontext` chunks first, then cuts the last kept chunk at a sentence end (bisection on length); question, answer and reference are never cut; the value carries `details["truncated"]`, `tokens_before`, `tokens_after`, the metric logs case id, metric, tokens and cap, the runner counts `judge_truncated`. A prompt that is over the cap even without any chunk is `not_applicable` (`judge_input_too_long`); `Judge.score` itself refuses a prompt over the cap with `LLMError` before any call, so Ollama never cuts silently
