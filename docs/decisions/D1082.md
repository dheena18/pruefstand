[T6.2a, owner decision on the #171 behaviour change] Timeouts stay unretried (D624/D1065) and keep counting as candidate errors in `error_rate` (no gate change), with three additions. (1) **Own counter:** the runner counts every case whose error is a client timeout (adapter "timed out after" or runner "timeout after", `runner.retry.is_timeout`) also as `RunManifest.counts["timeout"]` (key present only when > 0), and the PR comment shows a line "Timeouts: N cases timed out (scored as candidate errors in error_rate)." next to the informational lines. (2) **Post-run health:** when the executor's `health.sh` check after the run fails, the run is an infra `error` (re-dispatch), not a candidate failure; the classification function lives in the orchestrator (`gate_orchestrator.post_run.post_run_infra_error`, PR #170, T6.2a S7: tunnel check + `health.sh` without `--repair` under the lock, exit code mapped to the kind; the call itself belongs to `evaluate`, not built yet). (3) **Tier 1:** the tier-1 configs (`examples/live/*.yaml`, the e2e configs under `packages/pruefstand/tests/e2e/configs/`) wait **180 s** (`target.timeout_s` and `runner.timeout_s`, was 60 s) so one CPU latency spike on the hosted runner does not end a case at once; tier 2 stays at 360 s. A test asserts 180 s for every `examples/live` config.
