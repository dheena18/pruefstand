[T5.2b, review of #75] B1: `JUDGE_SIDE_REASONS` (`canary_in_input`, `no_judges`, `judge_quota`, `judge_cap`, `judge_not_selected`, `judge_input_too_long`, in `core.models.metric`) are left out of the pairing like a judge error (`gate.tables._fillable`, counted in `n_excluded`), never worst-filled; a real candidate `not_applicable` (`missing_chunks`, `hard_fail`, ...) is still filled. Tier 2 with `judge_mode=skipped` on either run makes the judged metrics informational (`judge_skipped`); such a tier-2 run is not promotable. The canary scope (`canary_in_input`, selection) applies only when a configured judge is external (D328: canaries may reach the local judge). M2: the registry fails closed (judges skipped) whenever ANY external judge, the fallback included, is configured; an empty registry only for a purely local setup. M1: `refusal_judged` is `not_applicable` unless the answer is ambiguous and the judge enabled (`not_ambiguous` / `refusal_judge_off`), so a phrase refusal cannot raise it; it is no longer gated in the example configs. M3: the token estimate counts digits 1, non-ASCII 1, other ASCII 0.4 (no offline gemma tokenizer; the catalogue tokenizer stays a follow-up needing a dependency decision). Minors: all chunks `used_in_prompt=False` is `not_applicable` (`no_context_used`); an unchecked family (opaque target) is recorded as `counts["judge_family_unchecked"]`
