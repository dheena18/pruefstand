[CI fix, tier-1 baseline after a fingerprint change; main red since 2026-11-10] `live-e2e.yml` compared every run to `live-baseline`, the artefact of the last green push run on `main`. When a merge changes the `eval_fingerprint` on purpose (citation metrics v2, D890; calibration epoch; judge-cut detection), `pruefstand gate` stops with `eval_fingerprint differs between baseline and candidate`, the push run goes red, and as only a green push run writes `live-baseline` it never gets replaced: a permanent red. Decision: the tier-1 step runs the candidate, then `pruefstand baseline fingerprint-check --candidate C --baseline B` (new small command, `pipeline/baseline_fingerprint.py`, prints `comparable`, `changed <fp> <fp>` or `unreadable`, exit 0, exit 3 for an unreadable candidate). Anything but `comparable` is treated exactly like "no tier-1 baseline" (X1.4, T1.12, D502): the gate runs against a second run of the same commit (judge skipped), hard fails and the `error_rate` absolute check decide as before, no paired statistics, and the comment starts with "Baseline not comparable: eval_fingerprint changed (baseline <fp>, candidate <fp>); gated against a second run of this commit". A push to `main` whose gate passes (`gate_rc == 0`; both baseline uploads now require it) uploads the new `live-baseline`, so the next run compares again. The gate itself stays pure and unchanged (a mismatch passed to `pruefstand gate` is still an error, exit 3, so a mismatch can never hide a hard fail); nothing changes for tier 2 (a missing fingerprint baseline there is still `INSUFFICIENT_DATA`/`failure` until `baseline-promote`) nor for the nightly (`live-baseline-nightly` is handled by the same step and so heals the same way). An unreadable baseline artefact (older schema, damaged download) is handled alike. Cost: one extra `pruefstand baseline` subcommand (`fingerprint-check`, listed in interfaces §15; the exit-code set 0-3 is unchanged), a deliberate fingerprint change costs one extra tier-1 run (about 5 min) on the first push.
