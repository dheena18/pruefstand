[T6.2a, D624 runner rule] The `pruefstand` runner never retries a timeout: `call_with_retry` ends a per-try timeout at once (`attempts == 1`), and `HttpTargetAdapter` raises a read/total timeout as `TargetError(transient=False)`; `httpx.ConnectTimeout` / `PoolTimeout` stay transient (the request never reached the target) and are reported as "connection failed". Main's root `pruefstand.yaml` (run by the executor with the `core` split) sets `runner.timeout_s: 360` (> 300 s, the rag-demo generator read timeout; concurrency stays 8), so `test_root_pruefstand_yaml_follows_the_tier2_runner_rule` passes and its strict `xfail` is removed. Tier 1 is affected only in that a slow call now fails once instead of being retried up to 3 times (HTTP 5xx and connection errors are still retried). **Review of #171:** the adapter's own deadline is `target.timeout_s` (httpx and `asyncio.timeout`, `adapters/http.py`), so the root `pruefstand.yaml` sets `target.timeout_s: 360` as well and the D624 config check uses `min(target.timeout_s, runner.timeout_s) > 300` (or concurrency <= 4); `WriteTimeout` is non-transient too (the target stopped reading a small body, i.e. it is stalled; a retry only queues more), `PoolTimeout` stays transient (nothing was sent). Owner decision still open: tier 1 (concurrency 2, 60 s timeouts) now fails on one CPU latency spike (1 error of 20 = `error_rate` 0.05 > 0.02) instead of retrying, and on tier 2 a short infra stall that surfaces as a client timeout is scored as a candidate error, not `error`. Follow-up T1.13c: rag-demo's 503 after its own generator timeout is still retried as a 5xx
