# Round 8 — cold read 4: UI design (senior product designer + frontend engineer)

Scope: SPEC §2.4, §5.1, §7.6, §9 (P8); `docs/architecture/{components,data-model,interfaces}.md`
(dashboard, report, rag-demo parts); `docs/engineering/testing-strategy.md` §3.10; prompts T1.9, T6.4,
T8.1, T8.2a, T8.2b, T8.3, T8.4, T8.5, T9.2. Question: is the UI designed well enough for an AI agent
to build a professional result?

Verdict: **no design spec existed.** The prompts define routes, a few components and tests, but no
wireframes, tokens, state model, copy, i18n mechanics, chart rules or responsive behaviour. An agent
would invent all of that per task, and three data gaps make parts of the PR comment and dashboard
impossible to build without computing in TS. New file: `docs/design/ui-spec.md` (IA, wireframes,
components, states, tokens, a11y, copy, PR comment + HTML report layout, test matrix, page → field →
source mapping). No existing file was edited.

Counts: **3 blocker · 16 major · 9 minor** (28).

Line numbers refer to the files as they are now.

## What is already good

- Hard rules are sound and testable: no metric computation in TS, generated types, runtime schema
  validation, no `dangerouslySetInnerHTML`, sanitised data with a `CANARY-` content test.
- Status-never-by-colour, `UNSUPPORTED_CONFIG` badge test, informational label, leak badge and
  INSUFFICIENT_DATA greying are specified with tests.
- UI tests run on real exported artefacts in a pinned Playwright container with deterministic
  settings, and Try-it is tested against the real stack (no route mocks).
