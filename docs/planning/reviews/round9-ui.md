# Round 9 — cold read 5: UI (senior product designer + frontend engineer)

Scope: `docs/design/ui-spec.md` (v2), `docs/spec/SPEC.md` (§5.1, §5.3, §7.2, §7.6, §11.1),
`docs/architecture/interfaces.md` §1.4, §2, §9, §10, §10.1, §16, `docs/engineering/testing-strategy.md`
§3.8 + §3.10, prompts T1.9, T6.4, T8.1, T8.2a, T8.2b, T8.3, T8.4, T8.5, T9.2. Baseline: `round8-ui.md`
(UI-01…UI-28). Already-fixed findings are not repeated. No file was edited except this one.

Questions:
1. Can every page and state be built from fields that exist in interfaces.md under the same names?
2. Would two frontend agents build the same UI?
3. Do the PR comment and HTML report layouts match the data?
4. Does the UI test matrix cover page × state × theme × language × viewport, and can it run from the
   committed fixtures?
5. Do the prompts cite the right ui-spec sections?

Verdict: the v2 spec is much better than v1. Field names now match interfaces.md almost everywhere,
and 26 of the 28 round-8 findings are fully fixed. Four problems remain at the build and test level:

- The §14 matrix cannot run from the fixtures as specified. One static build has one data tree, and
  pages are pre-rendered, so the empty-index and bad-schema states cannot exist in the same build.
- The Next.js file layout in T8.1 does not build as written.
- The T8.5 CSP blocks the inline scripts and styles that the site and `report.html` need.
- `DashboardSlices` is still a comment in interfaces.md, not a model.

Counts: **1 blocker · 8 major · 16 minor** (25).

  the i18n mechanics are static and testable.
