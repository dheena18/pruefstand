# Security

Prüfstand is a security tool: it tests tenant isolation and prompt injection. Its own CI, its judges
and its demo are attack surfaces too. This file is the threat model; every control maps to the test or
check that proves it. CI details: `ci-cd.md` §7; operations: `docs/ops/runbook.md`; topology:
`gpu-cluster.md` §1, §6 (round 10, D196–D209; round 11 Y1–Y7, D211–D247; proxy networking D242; round 13 P1/P2); decisions: ADR-0004, ADR-0005,
ADR-0006, ADR-0009, ADR-0012, ADR-0017.

## 1. Assets

| Asset | Why it matters |
| --- | --- |
| A40 cluster `cairo-s101lp` (shared with other users) | research hardware; it runs **only** one Ollama server for both GPUs (ADR-0018; loopback `127.0.0.1:11434`, models on the cluster's own disk `/data/dheena/Models`, ADR-0019; the server is started by the owner's `~/start-ollama.sh` and reused); no runner, checkout, Docker, data or secrets of ours live there, so code execution of ours on it is limited to the reviewed scripts in `/data/dheena/pruefstand-bin` (copied over SSH) |
| Executor VM `pruefstand-exec` (system user `pruefstand`: runner, orchestrator, `/var/lib/pruefstand/gpu.lock`, state, run dirs, caches, VM → cluster SSH key `/home/pruefstand/.ssh/id_ed25519_cluster`; rootful Docker; also the owner's development host with coding agents, C18) | the trusted execution host; compromise = control over gate results and the cluster login |
| Data root `/mnt/pruefstand` (plain directory on the VM disk, ADR-0019): baselines, backups, datasets; cluster model store `/data/dheena/Models` and scripts `/data/dheena/pruefstand-bin` | swapped models or scripts run on the GPUs; poisoned baselines hide regressions |
| Private executor repo `pruefstand-gate` (workflows, orchestrator, `baselines` index branch), the baseline files in the data root and the VM caches (X2.7) | a poisoned baseline or cache makes regressions look normal |
| Public repo `main` | source of truth for users |
| Secrets (full list, locations, scopes and rotation: `docs/ops/secrets.md`): `pruefstand-bot` App key (private repo + public environment `gate-router`, deployment branch `main`, P1.1) and `DASHBOARD_DATA_PAT` (private repo only), release App key, HF token, the optional demo's Cloudflare Tunnel token (VM, user `pruefstand` only) (no paid-API keys: free providers only, ADR-0009) | cost, publishing and write rights. The public repo holds the App key in environment `gate-router` (posting `pruefstand/gate` only) and release-time secrets in protected environments (`release`, `action-sync` (optional), `huggingface`; PyPI and TestPyPI via OIDC, `testpypi` deployment branch `main` only; the dashboard deploys to GitHub Pages with OIDC, no token) and **nothing that reaches the executor** (D108) |
| Public repo `dheena18/pruefstand-dashboard-data` (sanitised dashboard data, sha256 manifest, `heartbeat.json`) | what the dashboard shows and what `executor-health.yml` trusts; writable only through a fine-grained PAT scoped to this repo (`contents: write`), stored in the private repo |
| Backups (weekly `pruefstand-gate.bundle.tar.age`: git bundle of the private repo + baseline files, `age`-encrypted **as a whole**, X2.6) | the copy in the data root (inside the TrueNAS zvol snapshots) plus the mandatory weekly laptop copy (Y5.5, receipt + `backup-check`) are the only copies of baseline files and held-out canaries outside GitHub; never stored or copied in clear text; the private key exists only on the owner's laptop |
| Released artefacts (PyPI, GHCR, `pruefstand-action` / Marketplace, HF dataset) | supply chain for users |
| Private-tenant synthetic docs, public canaries, **held-out canaries** | they must stay private for the leak and contamination tests to mean anything |
| Gate decision integrity | a wrong PASS ships a regression; a wrong FAIL erodes trust |
| Demo (optional, on the VM behind a Cloudflare Tunnel, Y7.5) | a public endpoint on the trusted host; it can burn CPU and must not reach the executor |

## 2. Threat model (STRIDE-lite)

| # | Component | Threat | Scenario | Controls | Proven by |
| --- | --- | --- | --- | --- | --- |
| C1 | Executor runner (VM) | Elevation / Tampering | A PR (fork or same-repo) adds a workflow job with `runs-on: [self-hosted, a40]` | **no runner on the public repo**; the runner (on the VM, never on the cluster) is registered only to the private executor repo, which runs only its own workflows from its `main`; the executor pulls work, so the public repo holds no credential that reaches it (ADR-0005) | [HUMAN] monthly runbook item (`docs/ops/runbook.md` §6): `gh api repos/dheena18/pruefstand/actions/runners --jq .total_count` → `0`; drill: a PR adding a self-hosted job stays queued forever ("no runner") |
| C2 | Candidate execution | Elevation / Disclosure | Candidate code escapes its container, abuses the GPU servers, or exfiltrates data | candidate runs on the VM only as the image built by `build-images.yml` on a hosted runner without secrets, pulled by digest (signature = origin only); **no GPU (the VM has none) and no internet egress**: only the `--internal` network `gate-net` with the executor's `qdrant` and `rerank-cpu`, including the trusted `llm-proxy` at `http://llm-proxy:11500` (C16, D242), never the tunnel ports (firewalled to the `proxy-egress` subnet by rules in Docker's `DOCKER-USER` chain (container-to-container and egress) **and** in the dedicated `PRUEFSTAND-INPUT` chain hooked from `INPUT` (container → `172.17.0.1` traffic is delivered locally and hits `INPUT`, not `DOCKER-USER`), both applied by the oneshot `pruefstand-firewall.service`, D285 (`After=docker.service`, re-applied on Docker restart); the full ruleset is never flushed or reloaded through `nftables.service`, so Docker's own isolation rules for the `--internal` `gate-net` stay intact, N4.2/A12-02); containers started by user `pruefstand` through the rootful daemon (Y1.3); read-only root fs, no host socket, `--cap-drop ALL`, `no-new-privileges`, no `ipc: host`; the held-out canary **registry** is never mounted into or reachable by the candidate, which sees only the corpus through Qdrant over `gate-net` (X2.5). **Residual risk (R9-31, not adopted now):** the candidate runs under the same **rootful** Docker daemon as the persistent runner, so a container escape is root on the VM, with the runner's `.credentials` **and the VM → cluster SSH key** of `pruefstand` (C15); a separate VM for candidates is the documented upgrade path | T6.2a test: no candidate mount contains the canary registry or `PRUEFSTAND_HELDOUT_DIR`; the candidate `docker run` argv has no `--gpus`/`--device` and only `gate-net`; an egress probe and a direct connect to `172.17.0.1:11434` and to any other `172.17.0.1` port from the candidate fail; T0.7 `vm_check firewall`: the rules sit in `DOCKER-USER` and `PRUEFSTAND-INPUT`, Docker's chains (Docker >= 28: `DOCKER`, `DOCKER-FORWARD`, `DOCKER-BRIDGE`, `DOCKER-CT`, `DOCKER-INTERNAL`; older: `DOCKER-ISOLATION-STAGE-1/2`) still exist after `systemctl restart docker`, a throwaway container on an `--internal` network has no egress, and no shipped firewall file contains `flush ruleset`; the candidate argv has no `--add-host`/`host-gateway` and no `proxy-egress`; `pruefstand` has no sudo except the one `systemctl restart pruefstand-tunnel` line (`infra/gate-executor/host/check-host.sh`, in T6.2a Files/S9, ShellCheck clean) |
| C3 | Trigger | Spoofing | Someone (or a coding agent) makes the executor run an unreviewed SHA | no dispatch workflow and no executor credential in the public repo; the **only** tier-2 PR trigger is a `workflow_dispatch` of `gate-executor.yml` (input `pr`) in the private repo, started by the owner from the browser or the GitHub mobile app (round 13 P1.2); the VM token has no access to the private repo (C18), so agents cannot start it; there is no `run-gate` label and no PR poll; the executor gates the PR head at dispatch time, which must carry a `pruefstand/image` status; `main` pushes and nightlies are automatic | orchestrator unit tests on recorded API fixtures: dispatch for a non-gated PR → no run; head without `pruefstand/image` status → `pending`, no run; dispatch → run on the head SHA at dispatch time; `test_check_workflows.py`: `gate-executor.yml` has only `workflow_dispatch` |
| C4 | Fork PRs | Tampering / Spoofing | A fork smuggles workflow or executor changes through the `gate/pr-N` branch used for its image build, a mirror **PR** runs the fork's code with same-repo permissions, someone else pushes `gate/pr-N`, or the fork author pushes after review so a green result lands on unreviewed code | `scripts/mirror_fork_pr.sh` pushes only branch `gate/pr-N` and **never opens a PR** (D104); it refuses diffs touching `.github/**`, `infra/runner/**`, `infra/gate-executor/**`, `action/**`, `scripts/mirror_fork_pr.sh`. The owner's review, mirror and **dispatch** are the human approval for running foreign code (P1.2). **SHA check (X2.3):** at dispatch the executor reads the fork PR head SHA, gates `gate/pr-N` only if its head SHA equals it, and posts the status to that SHA only | unit test of the script on fixture diffs; `--dry-run` never prints `gh pr create`; T6.2a `test_jobs.py`: `gate/pr-N` ≠ fork head at dispatch → no run, pending on the current head; equal → status on that SHA only |
| C5 | Caches | Tampering | A PR job writes a forged "score 5" under a key main later reads | trust domains: only `baseline-promote.yml` / `nightly.yml` write `$PRUEFSTAND_HOME/pruefstand-cache/main` (VM disk); PR jobs mount it read-only plus a per-run overlay deleted in `cleanup` (ADR-0006) | `test_layered_cache.py` (overlay write never reaches the base, byte for byte), `test_cache.py` / `test_run_cache.py` (PR run leaves the shared cache untouched, overlay deleted) |
| C6 | Baselines | Tampering | A bad baseline is written | baselines are plain files in the data root on the VM disk (`$PRUEFSTAND_DATA_ROOT/baselines/`, single writer `baseline-promote.yml`, write-then-rename) with an `index.json` in the private repo's protected `baselines` branch (no force-push, X2.7); only `baseline-promote.yml` writes (including the monthly prune), with the private repo's `GITHUB_TOKEN` for the index; write access to the VM (user `pruefstand`, and the root-equivalent owner user, C18), the data root and the private repo is the trust boundary (no signatures); `manifest.json` holds a sha256 per file, its hash is in `index.json`, and both are checked on read; incomplete runs never promoted (ADR-0004) | `test_baselines_integrity.py` / `test_baselines_git.py`: sha256 mismatch → `StoreIntegrityError`, index pin, decompression bomb, symlinks, hostile fingerprints/refs; `test_gate_refs.py`: fingerprint mismatch → `GateInputError` |
| C7 | Gate bypass | Repudiation | A PR merges without a gate result (no dispatch, no baseline, cluster down) | the commit status `pruefstand/gate` is a required check **pinned to the `pruefstand-bot` App** (round 13 P1.1); `gate-router.yml` posts with the App token success "not gated" only when no gated path changed (or only release-exempt lines), otherwise `pending` "gated: awaiting tier-2 dispatch"; for gated PRs the executor App posts the result (`pending` while waiting for the GPU lock, `failure` "no baseline for <fp>" when no baseline exists, D103); ruleset bypass list = repository admin (the owner) only, for executor outages (VM, tunnel or cluster), used from the browser and verified to be unusable from the VM token (runbook §2.7), every bypass logged in `docs/ops/bypass-log.md` (D106) | orchestrator tests of the gated-path and no-baseline logic (no-baseline PR → never `success`); `gate-router.yml` unit test on fixture file lists (gated path → `pending`; release-exempt → success); drill: gated PR without dispatch stays blocked; bypass-log row per bypass |
| C13 | `gate-router.yml` | Elevation / Spoofing | The only `pull_request_target` workflow runs fork code with the App key, or a same-repo branch workflow posts a fake `pruefstand/gate` success | `gate-router.yml` has **no checkout step** and fetches no PR code (only the changed files and patches from the API), job permissions exactly `pull-requests: read`, and posts with the `pruefstand-bot` App token minted from the key in environment **`gate-router`** (deployment branches `main` only; `pull_request_target` always runs the `main` version, so a PR cannot change what runs with the key); the workflow guard allowlists exactly this file for `pull_request_target`, asserts no checkout and that no other workflow names environment `gate-router` or `secrets.BOT_APP_*`. **Status spoofing is closed by the pin (P1.1):** a branch workflow can request `statuses: write` and post `pruefstand/gate` with `GITHUB_TOKEN`, but that status comes from `github-actions`, not from the pinned App, so it cannot satisfy the required check. Residual: a branch workflow can name a job like another required check run; the owner's merge step (and the lead agent's pre-merge step) checks via the API that every required check run comes from its expected workflow file and that `pruefstand/gate` was created by `pruefstand-bot[bot]` | T0.2 `test_check_workflows.py`: `pull_request_target` only in `gate-router.yml`, no `actions/checkout`, exact permissions, environment and `BOT_APP_*` only there; zizmor; [HUMAN] T6.2b drill: a branch workflow posting `pruefstand/gate` = success leaves the PR blocked |
| C8 | Artefacts | Disclosure | Public Actions artefacts, logs or the dashboard-data repo expose chunk text, private docs or held-out canaries | full run dirs and baseline files on the VM disk (never public), baseline index only in the private repo; public PR comments redacted (no chunk text, canaries masked); dashboard data sanitised (no private-tenant text) before it is pushed to the public dashboard-data repo | snapshot test of the redacted comment; export test (`verify_dashboard_export.py`): no `CANARY-` token body and no private-tenant chunk text in dashboard JSON |
| C12 | Dashboard-data repo | Tampering / Elevation | The PAT leaks, or the public repo gains a token that reaches the private repo | fine-grained PAT `DASHBOARD_DATA_PAT` scoped to `pruefstand-dashboard-data` only (`contents: write`, expiry ≤ 1 year), stored only in the private repo; `deploy.yml` and `executor-health.yml` read the data repo anonymously; `deploy.yml` verifies the sha256 manifest; no `demo` or `preview` environment exists (D244); no public-repo token reaches `pruefstand-gate` (D108); the `pruefstand-bot` App installation covers the public repo only | T6.2b `test_check_workflows.py`: no public workflow references `secrets.DASHBOARD_DATA_PAT` or any `secrets.*PAT*`, and only `gate-router.yml` references `secrets.BOT_APP_*` (environment `gate-router`, P1.1); deploy dry-run with a mismatched manifest fails; rotation step in `docs/ops/runbook.md` §7 |
| O1 | Executor availability | Denial of service | The VM runner is offline, the tunnel or an Ollama server is down (cluster reboot), the data root unusable (`data_root_unavailable`, ADR-0019), the cluster model disk full, a GPU is taken by another cluster user, the disk is full, or the PAT expired; PRs sit at `pending` unnoticed, or every PR (even docs-only) waits for the executor | non-gated PRs get `pruefstand/gate` from the hosted `gate-router.yml`, never from the runner (X2.2); for gated PRs the GPU lock is taken first and the preflight (`health.sh --repair`: tunnel ports, restart of a down Ollama server over SSH, resident digests, data root writable with ≥ 20 GB free, `df`, free GPU memory and cluster `/data` space via `status.sh`) runs under it (X2.1, D208): lock timeout → `pending` "executor busy", preflight failure → `error` "executor unhealthy"; `heartbeat.json` (branch `heartbeat`) refreshed every 15 min during runs and lock waits (Y5.1); public `executor-health.yml` opens an issue when it is older than 2 h (D109); an infra failure **during** a run gives `error` (not `failure`), is not recorded as processed and is retried once after `health.sh --repair` (Y5.2), so a cluster or data-root fault never shows as a candidate FAIL; data root a plain directory on the VM disk (ADR-0019), VM autostart after a TrueNAS reboot (Y5.3); Ollama started with `setsid nohup` and relaunched by the preflight (Y5.4); `MAINTENANCE` file `/var/lib/pruefstand/MAINTENANCE` | [HUMAN] T6.2b drill: stop the runner → `executor-down` issue within 2 h, and a docs-only PR still gets "not gated"; T6.2a test: Ollama killed mid-run (stub) → `error`, not `failure`, not processed, one retry |
