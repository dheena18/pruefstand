## Goal

A public, abuse-resistant demo endpoint (rag-demo in "public mode") and a dashboard page where a
visitor picks a tenant, asks a German question and sees the answer with citations and chunks.

## Context

Public mode is a config profile `apps/rag-demo/configs/rag.public.yaml` (next to T1.13's `configs/rag.yaml`, selected with `RAG_CONFIG`), not a code fork. It adds two `RagConfig` fields, `public_mode: bool = False` and `public: PublicLimits | None = None` (rag-demo-local models in `rag_demo/models.py`; update interfaces §16 and flag under "Interface changes"). Controls:
1. **Rate limit** (ADR-0012 values):
   - 10 req/min and 100 req/day per client key; 2,000 req/day globally.
   - The client key is the IPv4 address or the IPv6 **/64 prefix** of **one** source (UI12-10): the
     `X-Forwarded-For` hop selected by `TRUSTED_PROXY_HOPS` (`1` behind the tunnel: cloudflared appends
     the visitor address as the last hop; `0` = the TCP peer address, used by `rag-demo-e2e`, where
     host connections through the published port arrive from the Docker bridge gateway, e.g.
     `172.x.0.1`, not from `127.0.0.1`; that key is stable for the run, which is all the e2e needs;
     UI13-04).
     `CF-Connecting-IP` is never read.
   - **In-process** token buckets and daily counters (one rag-demo process; no SQLite, no file). A
     process restart resets them; that is accepted (only the owner restarts the demo) and it is how the
     e2e isolates its groups (Y7.5).
   - The demo sits behind a Cloudflare Tunnel (ui-spec §4.6), so `TRUSTED_PROXY_HOPS=1`; rag-demo is reachable only
     from `demo-net` (where T8.5's `cloudflared` container calls `http://rag-demo:8000`) and on the host's
     `127.0.0.1:8090` (no path around the tunnel can forge the hop).
   - The 11th request in a minute → 429 `rate_limited`; per-key daily cap (`DEMO_DAILY_PER_KEY`,
     default 100) or global daily cap → 429 `daily_limit`. `Retry-After` header is still sent, but the
     contract is the JSON body (below).
2. **Daily compute cap** (free-only: no paid LLM API). The demo generator is the pinned CPU
   llama.cpp model from T1.13 running on the VM's CPU (no external LLM and no A40, so private demo
   docs and canaries never leave the VM). Generated tokens are tracked per UTC day, in-process.
   - Before each generation, the worst case (`max_tokens`) is **reserved** from the daily token
     budget; the real count is settled afterwards, so concurrent requests cannot overshoot.
   - Reaching `DEMO_DAILY_TOKENS` (default 200 000) or `DEMO_DAILY_REQUESTS` (default 2 000) → 503
     `budget_exhausted` (`retry_after_s` = seconds to 00:00 UTC).
   - Limits come from `public` in `rag.public.yaml`. rag-demo does not import `pruefstand`.
   - At most `DEMO_MAX_CONCURRENCY` (default 2) generations run at once so the free host stays
     responsive; overflow is **not queued**: 429 `busy`, `retry_after_s: 5`. A generation exceeding
     the server timeout `DEMO_TIMEOUT_S` (default **75**, below the client's 90; UI11-17) → 504
     `timeout`.
3. **Kill switch**: env `DEMO_ENABLED=false` or file flag `/run/demo/disabled` → 503 `demo_disabled` immediately,
   checked per request; also an admin endpoint is **not** provided (no remote write paths).
3b. **Test-only reset (N5.4, R13 P5.4, binding):** when, and only when, `DEMO_TEST_RESET=1`, rag-demo
   registers `POST /v1/_test/reset`, which empties the token buckets, the daily counters, the
   token/request budget and the concurrency slots, and returns 204 with no body. It answers only when
   the TCP peer address is loopback (`127.0.0.1` or `::1`; `X-Forwarded-For` is ignored for this check);
   any other peer → 404 (as if the route did not exist). **A host request to the published port is
   never loopback inside the container** (docker-proxy/DNAT: the peer is the bridge gateway, UI13-04),
   so the reset is always called **from inside the container**:
   `docker compose -p pruefstand-demo -f infra/deploy/demo/compose.yml exec -T rag-demo-e2e curl -fsS -X POST http://localhost:8000/v1/_test/reset`
   (the rag-demo image ships `curl`; add it in this task if T1.13's Dockerfile lacks it). **While any
   generation is in flight the reset returns 409** (`{"code": "busy", …}` body) and changes nothing;
   counters and slots are zeroed only when idle, so a still-running `T-BUSY` generation can never
   over-release a slot later (UI13-15). Without the env the route is not registered (404). Only the e2e
   instance `rag-demo-e2e` sets it, and it publishes only on `127.0.0.1` (defence in depth); the `demo`
   profile and `rag.public.yaml` never set it (asserted in tests).
4. Fixed tenant allow-list (`kanzlei_mueller`, `versicherung_nord`, `stadtwerke_sued`), question
   length ≤ 500 chars, top_k fixed, no `request_id` from client, CORS only for the dashboard origin,
   request body size limit, no logging of question text beyond a hash + length.
5. Synthetic private docs with canaries stay indexed (that is the demo of isolation), but the public
   index uses the **published** canary set only, never the held-out one.
6. **Licence notices** on `/try` and in API responses' docs: the sources and licences from
   `DATA_LICENSES.md`, including the ODbL notice for Open Legal Data content and the offer of the
   derivative database, plus CC BY 4.0 attribution (GermanQuAD/DPR/RAG) and ODbL (OLDP) where relevant.
7. **Error body (W5.5, interfaces §16, D138):** every 4xx/5xx in public mode is JSON
   `{"code", "message", "retry_after_s"}` with `code` ∈ `rate_limited | daily_limit | busy |
   budget_exhausted | demo_disabled | invalid_request | body_too_large | timeout` (HTTP status per
   ui-spec §4.6 table; 422 → `invalid_request`, 413 → `body_too_large`). `message` is English for API
   users; the UI never shows it. CORS: only the dashboard origin; `Access-Control-Expose-Headers:
   Retry-After` kept for other clients.

The dashboard page `/[locale]/try/` calls `NEXT_PUBLIC_DEMO_API_URL`; in static export it is a client
component. It implements ui-spec §4.6 exactly: wireframe, the pure state reducer with every `T-*`
state (disabled, idle, invalid, loading with elapsed counter + Cancel + double-submit guard, slow
> 10 s, client timeout `NEXT_PUBLIC_DEMO_TIMEOUT_S` default 90, cancelled, success with focus on the
answer heading, refused badge, rate-limited/busy countdown from `retry_after_s`, daily limit, budget,
demo off, rejected, network, server error), one `aria-live` region, error panels `role="alert"`, all
copy from ui-spec §10.4 (de + en). Without `NEXT_PUBLIC_DEMO_API_URL` at build there is no nav link and
the page shows `try.unavailable` (UI-25). `src/content/try.json` has the ui-spec §4.6 shape
(`tenants: [{id, label: {de, en}, description: {de, en}}]`, `examples`, `refusal_example`): ≥ 1 real
slice-corpus question with a verified answer per tenant, and one verified question the real app
refuses (for `T-REFUSED`). UI details fixed by ui-spec §4.6 (UI9-21): at load the question is empty,
the state is `T-IDLE`, Ask is disabled and no error shows; validation runs on input after the first
input and on submit (`T-INVALID`), never on blur; the textarea and the examples are `lang="de"` also
on `/en`; the limits line is `try.limits` without numbers; a response chunk with
`used_in_prompt == false` shows `try.not_in_prompt` (X3.14). The page's CSP `connect-src` is the demo
API origin, set by T8.1's `csp.mjs` from `NEXT_PUBLIC_DEMO_API_URL`; no inline script or `style`
attribute (ui-spec §7.4).

`rag.public.yaml` sets `reranker: off` (the interfaces §16 default; the `demo` profile has no `rerank`
service; UI11-16).

**Try-it e2e (Y7.5, UI11-07, N5.4, UI12-04, UI12-11, UI12-12; ui-spec §14.2 "Try-it run", binding):**
runs on the VM against **one** demo instance, never on a hosted runner, never as a PR check and never as
a `ui.yml` job. `scripts/demo/try_e2e.sh`:
0. runs `pnpm install --frozen-lockfile`, both builds and Playwright **inside the pinned Playwright
   image** (the visual-baseline image) with `--network host`, mounting the job's disposable checkout of
   trusted `main`; the service user `pruefstand` needs only Docker (no Node, pnpm or browsers; UI12-12);
1. computes `E2E_PORT=$((8091 + ${PORT_OFFSET:-0}))` (Y1.4: `PORT_OFFSET=10000` when an agent runs it)
   and uses it for the compose port and for `NEXT_PUBLIC_DEMO_API_URL=http://127.0.0.1:$E2E_PORT`;
2. builds `build_set.sh populated --out populated-try` and `build_set.sh populated --out
   populated-try-timeout` (same URL, `NEXT_PUBLIC_DEMO_TIMEOUT_S=1`); serves `populated-try` with
   `serve -l 4175` for every group, and for `T-TIMEOUT` (run last) stops it and serves
   `populated-try-timeout` on 4175, so both share `DEMO_ALLOWED_ORIGIN=http://localhost:4175`;
3. uses the e2e instance `rag-demo-e2e` (compose project `pruefstand-demo`, profile `e2e`, published
   only on `127.0.0.1:$E2E_PORT`), which shares the demo's Qdrant, `llm` and `embed` services and never
   touches the public `rag-demo`; its env adds `TRUSTED_PROXY_HOPS=0` (browser and test call it
   directly, so the key is the peer address rag-demo sees, the bridge gateway, stable for the run) and
   `DEMO_TEST_RESET=1`;
4. starts **one** long-lived Playwright container (`docker run -d --network host … sleep infinity`) and
   runs `try.spec.ts` (`workers: 1`, `fullyParallel: false`) group by group; before each **group** it
   restarts `rag-demo-e2e` with the group's env (env changes need a restart) and waits for `/v1/health`.
   Groups: defaults (`T-IDLE`, `T-INVALID`, `T-LOADING`/`T-SLOW`, `T-CANCELLED`, `T-SUCCESS`,
   `T-REFUSED`, then `T-TIMEOUT` on the timeout build), `DEMO_RATE_PER_MIN=1`, `DEMO_MAX_CONCURRENCY=1`,
   `DEMO_DAILY_PER_KEY=1`, `DEMO_DAILY_REQUESTS=0`, `DEMO_ENABLED=false`, container stopped
   (`T-NETWORK`);
5. **before each of the 8 combinations** of every row (R13 P5.4): the script lists the group's tests
   (`playwright test e2e/try.spec.ts --list --reporter=json`, one entry per row × project × theme ×
   locale), and for each one runs the in-container reset above (expects 204; on 409 it retries every
   2 s for ≤ 60 s, then fails naming the test; skipped only for `T-NETWORK`, where the container is
   stopped), then `docker exec <pw> pnpm exec playwright test e2e/try.spec.ts --project <p> -g '<exact
   title>'`. No combination inherits another's limit state (N5.4). The spec itself never calls the reset
   (the Playwright container has no Docker access, and its HTTP call would not be loopback);
6. limit rows reach their state **without a page-side success** (UI12-04): after the reset,
   `T-RATE-LIMITED` and `T-DAILY-LIMIT` send one real pre-request with Playwright `request.post` (same
   client key), then the page's first request gets `rate_limited` / `daily_limit`; `T-BUSY` sends one
   real query with `request.post` and, once the server has accepted it, submits from the page while it
   still runs, and its `afterEach` **awaits that background request to completion**, so the next reset
   finds the instance idle (UI13-15); `T-BUDGET` and `T-DEMO-OFF` need no generation;
7. `T-LOADING`, `T-SLOW` and `T-CANCELLED` hold the real `/v1/query` response with T8.3's
   `e2e/delay.ts` (delay only, X1.2), so no row depends on model speed. Real generations: `T-SUCCESS`,
   `T-REFUSED`, `T-BUSY` and the one pre-request of `T-RATE-LIMITED` and `T-DAILY-LIMIT` = 5 × 8 = 40.
Budget (ui-spec §14.2): builds ≤ 8 min, 7 restarts ≤ 4 min, 40 generations at ≤ 30 s ≤ 20 min, other
combinations ≤ 8 min, one `docker exec` + reset per test (≈ 104 × ≤ 2 s) ≤ 4 min → ≤ 44 min wall time. The nightly schedule is job `demo-e2e` of T8.5's private
executor workflow `demo-nightly.yml` (after `demo-deploy`, 06:15 Europe/Berlin, `timeout-minutes: 45`;
D244), which calls this script. `T-DISABLED` stays in T8.3's PR matrix.

## Interfaces (must match `interfaces.md` exactly)

```text
POST /v1/query
  request : {"tenant_id": str, "question": str, "top_k": int | null, "request_id": str}
  response: {"answer": str, "citations": [str], "chunks": [{..., "used_in_prompt": bool | null}], "refused": bool | null, "model": str | null, "usage": {...} | null}
```

In public mode the server generates `request_id` and ignores client `top_k`; the response shape is unchanged.
Errors in public mode: `{"code": "rate_limited" | "daily_limit" | "busy" | "budget_exhausted" | "demo_disabled" |
"invalid_request" | "body_too_large" | "timeout", "message": str, "retry_after_s": int | null}` (interfaces §16, D138).
