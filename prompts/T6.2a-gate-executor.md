## Goal

The executor VM `pruefstand-exec` can evaluate a given public commit SHA safely, using the A40s only through the one
Ollama server on the cluster `cairo-s101lp` (ADR-0018), reached through the VM's `autossh` tunnel (round 10 Z1). A
private executor **on the VM**:
- pulls the signed candidate image by digest and runs it on the VM's rootful Docker (as user `pruefstand`), with **no GPU and no internet**;
  its only route to a model is the trusted **`llm-proxy`** (built here, D206);
- loads the requested catalogue models into Ollama through T3.1a's scripts and uses a PR-scoped index when needed;
- runs the **trusted** `pruefstand` with the **trusted** gate config and dataset;
- reports a redacted result back as commit status `pruefstand/gate`.

No self-hosted runner is ever attached to the public repo, and the public repo holds no executor secret (its only
gate-related secret is the `pruefstand-bot` App key in environment `gate-router`, round 13 P1.1).

- **Persistent runner (W2.1, D100, D211).** User `pruefstand` runs a **persistent (not ephemeral)** GitHub Actions

  No App for runner registration. **Runner updates (A13-M9):** auto-update stays **on** (GitHub stops assigning jobs to a
  runner that falls about 30 days behind a release); `ExecStart` is the runner's own `run.sh` (which restarts the
  listener after a self-update), never `Runner.Listener` directly; the pinned release + sha256 applies to the first
  install only. The heartbeat carries `runner_version`; runbook §6 compares it with the latest release.
- **Job hygiene hooks.** The runner `.env` sets `ACTIONS_RUNNER_HOOK_JOB_STARTED=…/host/job_started.sh` and
  `ACTIONS_RUNNER_HOOK_JOB_COMPLETED=…/host/job_completed.sh`. Both: wipe the job workspace (`_work/`), remove
  containers, networks and volumes labelled `pruefstand.job`, drop PR-scoped Qdrant collections `pr_*` and
  `pr-*` cache overlays. They are idempotent and never touch the shared cache, baselines, model weights or the
  owner's dev stack (compose profile `dev`, `PORT_OFFSET=10000`, Y1.4).
  This is acceptable because only private, trusted workflows run on the runner and the candidate is sandboxed.
- **GPU lock (round 9 X2.1 + round 11 Y1.1/Y1.2, binding; single definition in `docs/engineering/ci-cd.md` §1.2).**
  The **orchestrator takes `flock -w <timeout> /var/lib/pruefstand/gpu.lock` exactly once per job** (fixed host-wide
  path on the **VM's local disk**, never in the data root and never under a home directory; wait ≤ 2 h for PR and promote
  jobs; the nightly's lock wait counts against its 8-h window budget, Y4.3) and exports `PRUEFSTAND_LOCK_HELD=1` to its
  children. The owner's and agents' GPU commands (`mk/gpu.mk`, T5.4, T6.3, T7.x) take the **same file** through
  `pruefstand-lock`, so a dev mode switch can never run inside a gate job. `infra/gpu/switch-mode.sh`,
  `infra/gpu/health.sh` and `infra/gpu/fetch-model.sh` are **created by T3.1a**; they **never take the lock** and
  refuse to run unless `PRUEFSTAND_LOCK_HELD=1`, so a phase switch or generator swap inside a job cannot deadlock
  on its own parent. This task only **calls** them. Concurrency groups are **per workflow** (T6.2b), never one
  shared `gpu-cluster` group.
- **Order of every job (X2.1, R9-02):** `MAINTENANCE` check (the file `/var/lib/pruefstand/MAINTENANCE`, Y1.2) →
  `select_jobs` (the dispatched PR, round 13 P1.2; no GPU work when it yields no job) → `flock -w` → **preflight** under the lock → serve → run.
  **Preflight (D200, D208, D227, D228)** = `systemctl is-active pruefstand-tunnel` (system unit; if inactive, one
  `sudo systemctl restart pruefstand-tunnel`, the only `sudoers` line `pruefstand` has) → **`infra/gpu/health.sh --repair`** in the **job's mode** (the Ollama server answers
  through the tunnel, else `start-ollama.sh` over SSH starts one server detached with `setsid nohup` only if none runs,
  wait ≤ 5 min; data root check (exists, writable, ≥ 20 GB free, sentinel; exit 16, ADR-0019); catalogue models outside the job's mode (an e5 or RQ2 candidate left by a killed job) unloaded;
  the mode's models resident with catalogue digests and fully on the GPU (`size_vram == size`, not spread over both
  cards; exit 15 otherwise, ADR-0018), else loaded with the catalogue `options`; free VRAM per card and free space on the cluster's `/data` from `status.sh`; `/data/dheena/pruefstand-bin` up to date) → `df` on
  `$PRUEFSTAND_HOME`. A cluster or TrueNAS host reboot therefore needs no manual step. An unusable data root fails the
  job in the preflight with `error` "executor unhealthy: data root unavailable", logged and sent in the heartbeat
  `last_result` as `infra_error="data_root_unavailable: <detail>"` (ADR-0019). Outcomes (nothing is recorded
  in `processed.jsonl` for any of them; all posted with **`GitHubPublisher.post_status(sha, state, description)`**,
  round 13 P4.2, never `set_check`): `MAINTENANCE` present → `pending` "executor in maintenance; dispatch again
  later", no lock taken; lock timeout → `pending` "executor busy (GPU lock held); dispatch again" (there is no
  PR poll that would retry); preflight fails under the lock → `error` "executor unhealthy: <reason>".
- **Infra failure mid-run (round 11 Y5.2, D226, binding; round 12 N6.1/N6.4).** The orchestrator reads `llm-proxy`
  `GET /health` → `{"model_reloads": int, "upstream_errors": int, "requests": int}` (cumulative since proxy start;
  interfaces §1.5) **before and after** `pruefstand run` and writes the deltas into the run's
  `RunManifest.counts["model_reloads"]` and `counts["upstream_errors"]` with **`ArtifactStore.add_counts`** (T1.8,
  D267) before upload or promotion. After the run it also
  re-runs `health.sh`. Ollama down, tunnel lost, data root unavailable during the run, an `upstream_errors` delta > 0, a
  resident-digest change, or a **model reload during the run** (`model_reloads` delta > 0: a forwarded response with
  `load_duration` > 1 s after the preflight; SPEC §6.2) → the run is `stop_reason="aborted"` with
  `RunManifest.infra_error = "<kind>: <detail>"` (D245; kinds `ollama_down`, `tunnel_lost`, `data_root_unavailable`,
  `proxy_upstream`, `model_reload`, plus `window_exceeded` for the nightly deadline, T6.2b/N4.3), and the commit status
  is posted with **`set_check(sha, "error", summary, infra_error=True)`**, which yields exactly the interfaces §10 text
  **`"executor infra error: <summary>"`**, where the summary is `"<kind>: <detail>; retrying once"` on the first
  failure and `"<kind>: <detail>; re-dispatch to retry"` after the second (**never `failure`**: the candidate is
  not blamed and no case is scored as a candidate error; no other wording such as "executor unhealthy during run"). Nothing is promoted; the orchestrator runs `health.sh --repair`
  and **retries the job once** in the same lock hold. A second infra failure posts `error` with the
  "; re-dispatch to retry" summary (no further retry) and **is** written to `processed.jsonl` with
  `result: "error"` (round 12 A12-M1); only a new owner dispatch runs it again. A nightly `window_exceeded` abort is never
  retried and never promoted. The judge side (trusted, same Ollama server, called
  directly through the tunnel, not behind the proxy) has no separate counter: judge errors go to `judge_error` / `judge_degraded` (D120), and a judge
  reload shows as a resident-digest or `health.sh` failure after the run.
- **Heartbeat (round 11 Y5.1, D225).** A background thread of `evaluate` calls T6.1 `push_heartbeat` **every 15 min**
  while a job runs and while waiting on `flock`, plus once at the end of every job, so `executor-down` never fires
  during a healthy 8-h nightly.

**`llm-proxy` (round 10 D206 + round 11 Y3.2 and the integration decision D242 that supersedes Y1.5/D215, D220,
built here; contract in interfaces.md §1.5).** Ollama has no API key and its API can pull, delete and unload models,
so the candidate never talks to Ollama directly. `llm-proxy` is a small trusted service (Dockerfile per CLAUDE.md
§8; module `llm_proxy.py`, D232) that runs as a **normal container** (never `network_mode: host`) attached to two
networks: the `--internal` network **`gate-net`** (where the candidate reaches it as `http://llm-proxy:11500`; no host
port) and the small non-internal bridge **`proxy-egress`** (subnet `10.231.0.0/24`, created by T0.7 and declared
`external: true` in `compose.executor.yml`). Its only upstream is `LLM_PROXY_UPSTREAM=http://172.17.0.1:11434`: the
tunnel to the one Ollama server (ADR-0018), which T0.7's `autossh` also binds on the Docker bridge gateway, reached over
`proxy-egress`; the VM firewall accepts `172.17.0.1:11434` only from the `proxy-egress` subnet (T0.7; rules in
`DOCKER-USER` and `PRUEFSTAND-INPUT`, D285). The judges run on the **same** server, so the model allow-list below is the
generator/judge separation: a judge tag (or any other tag outside the run's generator + embed set) is never forwarded (403). It forwards **only** `POST /api/chat`,
`POST /api/embed` and `GET /api/tags` (native API, Y3.1; every `/v1/*` path → 403), and only when the request's
`model` is one of the run's catalogue generator / embedding tags (passed by the orchestrator at start). **Option
policy (round 12 N2; supersedes the "replace all options" rule of Y3.2/D220):** the proxy enforces **only `num_ctx`
and `keep_alive`** (plus the model allow-list): `num_ctx` is always set to that model's catalogue value from
`infra/gpu/models.yaml`; every other **load-time** key (`num_gpu`, `num_batch`, `num_thread`, `use_mmap`, `main_gpu`,
`low_vram`, `num_keep`, and any key not listed below) is stripped; any `keep_alive` field is **stripped**. So a
candidate can neither reload, CPU-offload nor unload the shared generator. The **sampling** options `temperature`,
`seed`, `top_p` and `num_predict` **pass through** from the client when they lie within the catalogue entry's
`option_bounds` (T3.1a; e.g. `temperature` [0, 1], `top_p` [0, 1], `num_predict` [1, catalogue `num_predict`]); a
missing key (e.g. `seed`) gets the catalogue value (catalogue values are defaults, not overrides); a value outside its
bounds → 403 `{"error": "option out of bounds: <name>"}`, nothing forwarded, not counted as an upstream error.
Mutation M17 (generation temperature) and the T6.3 churn runs (`temp03`, per-run seeds) therefore reach the
generator as designed. It answers 403
`{"error": "<reason>"}` for any other path (`/api/pull`, `/api/delete`, `/api/create`, `/api/copy`, `/api/generate`,
`/api/ps`, `/v1/*`, …), any other model name and a missing/wrong `Authorization: Bearer
$PRUEFSTAND_CANDIDATE_API_KEY` (constant-time compare); it caps body size and per-request time, logs no bodies, and
counts upstream (Ollama/tunnel) errors separately from client errors on `GET /health` →
`{"model_reloads": int, "upstream_errors": int, "requests": int}` (round 12 N6.4, interfaces §1.5; cumulative since
start; `model_reloads` = forwarded responses with `load_duration` > 1 s, SPEC §6.2; `requests` = forwarded requests). **Verify** on the pinned Docker Engine that a container attached only to the
`--internal` network `gate-net` reaches `http://llm-proxy:11500`, `qdrant` and `rerank-cpu` and nothing else: no
`172.17.0.1` port (incl. `:11434`), no other VM host port, no internet. Only `llm-proxy` is on
`proxy-egress`; never attach the candidate to `proxy-egress` or any other non-internal network. No judge model is
reachable from `gate-net`: `llm-proxy` answers 403 for every judge tag (ADR-0018).

**PR trigger (round 13 P1.2, binding; supersedes the `run-gate` label rule of W2.3/R9-30).** Tier 2 for a PR starts
**only** when the owner dispatches `gate-executor.yml` in the private repo with input `pr=N` (browser or GitHub mobile
app). There is no `run-gate` label and no PR poll. The VM token has no access to the private repo, so no agent can
start tier 2, and the required `pruefstand/gate` is pinned to the App `pruefstand-bot` (P1.1), so no branch workflow
can satisfy it. `select_jobs` takes the dispatch (`pr`, `github.triggering_actor`) and the PR data from the public
API: the actor must be in `infra/gate-executor/maintainers.txt` (else exit 2, no status: defence in depth, only
users with write access to the private repo can dispatch at all); a PR without gated paths → **no job** (log "not
gated: gate-router owns the status"); the target SHA is the PR's **current head**, which needs a `pruefstand/image`
status from `build-images.yml` (else `post_status(head, "pending", "awaiting signed image; dispatch again after
build-images")`, no job). `main` pushes (baseline-promote) and nightlies stay automatic.

**Processed-work state (W2.3, D102, D145; R9-16).** The executor keeps `state/processed.jsonl` on the private repo's
branch `executor-state` (written only by `gate-executor.yml` with the private `GITHUB_TOKEN`), one line per
finished job: `{pr, head_sha, dispatch_run_id, result, run_id, at}` (ci-cd.md §1.2). It is a record, not a filter:
every owner dispatch runs (a re-dispatch is the retry after an infra error). Statuses are posted only when state or
description differ from the current `pruefstand/gate` status (read the combined status first; GitHub caps 1 000
statuses per SHA and context).

**Non-gated PRs (round 9 X2.2; round 13 P1.1/P4.2, binding).** The executor **never** posts any "not gated"
status: PRs that touch no gated path get `pruefstand/gate` = success "not gated (no gated paths changed)", and
release-please PRs that touch only the release-exempt lines get "not gated (release version bump)", both from the
public, hosted `gate-router.yml` (`pull_request_target`, no checkout, **`pruefstand-bot` App token** from
environment `gate-router`; T6.2b), so they never wait for the A40 runner. `select_jobs` returns **no job** for a PR
without gated paths; a dispatched release-please PR is gated like any other PR (the owner's choice).

**No baseline (W2.4, D103).** `pruefstand gate --from-store` exits 0 with `GateReport.no_baseline = true`
(`INSUFFICIENT_DATA`, T6.1). For a gated PR the orchestrator maps that to `pruefstand/gate` = **`failure`**
"no baseline for <fp>; run baseline-promote" by calling `set_check(sha, status, summary,
no_baseline=report.no_baseline)` (interfaces §10, the single mapping table, round 9 X4.6). Never `success`,
never an ad-hoc main run.

**Fork PRs (W2.5, D104; round 9 X2.3; round 13 P1.2, binding).** The owner reviews the fork diff, pushes the head to
branch `gate/pr-N` in the public repo (no mirror PR; `scripts/mirror_fork_pr.sh --reviewed`, T6.2b; this human step
is the real approval for running foreign code), then dispatches `gate-executor.yml -f pr=N`. `build-images.yml`
builds and signs the image from `gate/pr-N`'s head SHA. At dispatch the executor gates `gate/pr-N` **only if** its
head SHA equals the fork PR's current head SHA, and posts `pruefstand/gate` and the comment **to that SHA only**. If
they differ (the fork author pushed after mirroring): no `gate` job, `post_status(<fork head>, "pending", "fork head
moved since mirroring; re-run mirror_fork_pr.sh")`. A later fork push gets no result until the owner mirrors and
dispatches again. There is no `state/fork_labels.jsonl`.

**Held-out canaries (round 9 X2.5, binding).** The held-out canary **registry** (`PRUEFSTAND_HELDOUT_DIR`, the
private repo's `canaries/heldout/`) is read only by trusted executor steps (`pruefstand run` for the probes,
`sanitise_run`); it is never mounted into the candidate container, never passed in its env, and not reachable
from `gate-net`. The candidate sees only the corpus through Qdrant.

**Health and dashboard data (W2.9, W2.10, D108, D109; R9-21; round 11 Y5.1, A11-07).** Every 15 min during a job
and during a `flock` wait, and at the end of every job, the orchestrator calls T6.1 `push_heartbeat(repo, {ts,
last_job, last_result, runner_version, tunnel_ok, ollama_gpu0_ok, ollama_gpu1_ok, data_root_ok, disk_free_gb,
last_nightly_result, last_nightly_status, last_nightly_at, laptop_backup_age_days, tunnel_ok_false_since,
ollama_gpu0_ok_false_since, ollama_gpu1_ok_false_since, data_root_ok_false_since, maintenance})` (round 12 N4.3/A12-M2,
round 13 A13-M3: `last_nightly_status` is one of `ok`, `failed`, `aborted: window_exceeded`, `skipped: maintenance`,
`skipped: runner busy`, `skipped: preflight <reason>`; `last_nightly_at` changes only for `ok`/`failed`, so the 26-h
watchdog still fires on a series of skips; A13-M4: `maintenance` = `/var/lib/pruefstand/MAINTENANCE` present; each `*_false_since`
is the ISO time the field first turned `false`, empty while `true`, kept in `$PRUEFSTAND_HOME/state/health_since.json`
