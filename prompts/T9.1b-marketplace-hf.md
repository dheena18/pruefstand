## Goal

Each release produces two things:
- **(optional tier)** a synced public repo `dheena18/pruefstand-action` that can be listed on the
  GitHub Marketplace. Without it, the Action is used straight from the monorepo:
  `uses: dheena18/pruefstand/action@vX.Y.Z` — this is the documented default;
- **(core tier)** a manually dispatched HF dataset release with **freshly rotated** canaries and license-homogeneous
  configs, which cannot contain held-out canaries.

## Context

**Marketplace (optional; do S1 and S5's Marketplace step only if the maintainer opts in):** the
Marketplace needs `action.yml` at the repo root, one action per repo, and (verify the current rules) no
workflow files.
- Job `sync-action-repo` in `release.yml` uses the `pruefstand-release` App token (installed on the
  action repo too), minted in its **own environment `action-sync`** (deployment policy: tags `v*`; holds the same
  App id/key). Environment `release` allows only branch `main`, so a tag-triggered job cannot enter it (round 9
  R9-20). The App is therefore used by `release-please.yml` (env `release`) and the optional `sync-action-repo`
  job (env `action-sync`) only. It copies `action/action.yml` (image `:vX.Y.Z`, as in T9.1a), `action/README.md` and `LICENSE` into the action repo root, commits, tags `vX.Y.Z`
  and moves `v1`.
- The first Marketplace publication is a human step: the Release UI with "Publish this Action to the
  GitHub Marketplace".
- Until (or unless) the listing exists, docs show `uses: dheena18/pruefstand/action@vX.Y.Z`.
- The action is Linux-only, because Docker container actions are. The README explains how to reach a
  target started in an earlier step (`services:` or the job network) instead of `localhost`.

**HF release:** `dataset-release.yml` (`workflow_dispatch` only, `environment: huggingface`):
1. builds the release dir from public files only (`scripts/release/build_release_dir.py --out build/hf`);
2. runs `scripts/release/check_canaries.py`;
3. runs `export_hf(dir, repo_id, private, dry_run=True)` (round 8 W4.6, D132), which builds the HF layout
   (one config per `license_config`) under `dir / "hf_export"` and uploads nothing; `check_canaries.py` and the
   licence check run on **that** directory, so exactly what will be uploaded is checked;
4. uploads per license config with `export_hf(dir, repo_id, private=…)` (signature as in interfaces §14; call
   sites pass the bool by keyword, ruff `FBT003`, round 9 D9-36);
5. runs the informational `contamination-probe` job (`scripts/contamination_probe.py`, T4.6) on the released
   split and attaches its report to the run summary (security.md DA1: per dataset release).

The held-out set lives only in the private executor repo, so the public build cannot see it.
The check enforces this by construction:

| Check | Rule |
| --- | --- |
| (a) rotation | the current published registry shares no token or semantic fact with any entry in `datasets/canaries/retired.json` |
| (b) no private files | no file under `datasets/private/` or matching `*heldout*` is in the upload set |
| (c) only registered tokens | every `CANARY-[A-Z]{2}-[0-9a-f]{6}` token found in the upload set (after separator normalisation) is in the **current** registry; anything unknown fails |
| (d) licences | every config is license-homogeneous; no config mixes ODbL and CC BY-SA material |

After a successful upload the job writes the updated `datasets/canaries/retired.json` (every canary of the just-published registry appended as `{token, tenant, fact, retired_in: <release>}`, T4.6 format) and uploads it as artefact `retired-json`; the workflow has only `contents: read` (ci-cd.md §1.1), so the maintainer commits that file in a normal PR.
