## Goal

The **same** rag-demo app from T1.13 runs against the tier-2 stack: a `configs/rag.gpu.yaml`
selects catalogue models served by **Ollama on GPU0** of the cluster (generator `qwen3.8:27b-q8_0` with
thinking off, embeddings `bge-m3`; reached through the VM tunnel `OLLAMA_GPU0_URL`) and, later, the
**VM CPU reranker** `rerank-cpu` (`RERANK_URL`). rag-demo itself runs as a container **on the VM**
(`pruefstand-exec`), next to Qdrant. `/v1/info` reports the real catalogue ids, family and serving stack;
nothing in the CPU `live` profile breaks. No new app is created.

## Context

- rag-demo v0 already has the FastAPI app, `RagConfig` with bug switches, `config_hash`, OpenAPI
  contract, Dockerfile and the CPU `live` profile (T1.13). Keep all of it; tier-1 CI must stay green.
- **Native Ollama API in tier 2 (Y3.1, D219).** Tier 1 keeps llama.cpp's OpenAI-compatible `/v1` (CPU), so
  `LlamaCppGenerator` becomes `OpenAICompatGenerator` (rename + keep behaviour; tier 1 only). Tier 2 talks to
  Ollama **only** through `POST /api/chat` with `"think": false` and `options` = the catalogue `num_ctx` (8192, the
  only load-time option; `llm-proxy` enforces it) plus the sampling options from the config's `generation` section
  (round 12 N2, supersedes "catalogue options only" of Y3.2/D220: `temperature`, `seed`, `num_predict` =
  `max_tokens`, within the catalogue `option_bounds`; `top_p` from the catalogue), never
  `/v1/*` (Ollama ignores `options` there and truncates silently). So `generator` gains
  `engine: Literal["llama.cpp", "ollama"]`; this task adds the config field and a minimal `OllamaChatGenerator`
  (native body, options, no `keep_alive`); T3.6 finishes it (prompt, citations, think-stripping, bearer header).
  Embeddings: tier 1 keeps TEI CPU (`live`); tier 2 uses Ollama `/api/embed` with `bge-m3`, so `embed` gains
  `engine: Literal["tei", "ollama"]` (encoder classes: T3.4).
- **Bearer key (Y2.1, D216; DEV11-01).** `llm-proxy` rejects requests without
  `Authorization: Bearer $PRUEFSTAND_CANDIDATE_API_KEY`. `generator` and `embed` gain
  `api_key_env: str | None = "PRUEFSTAND_CANDIDATE_API_KEY"` (pre-approved interfaces §16 addition); the
  clients that send the header are T3.4 (embeddings) and T3.6 (generator); T1.13's tier-1 client already has it
  (empty key → no header). `rerank` has **no** key (D217: `rerank-cpu` has no auth).
- **No vLLM or TEI on the GPUs, no Docker on the cluster** (round 10 Z1/Z3). The `gpu` compose profile on the
  VM holds `qdrant` and `rerank-cpu` (T3.1a); rag-demo joins it here.
- **How the container reaches GPU0 (D242, supersedes Y1.5/D215).** In gate runs the candidate sits on the internal network
  `gate-net` and reaches Ollama only through the trusted **`llm-proxy`** (built in T6.2a; a normal container on
  `gate-net` + `proxy-egress`); the candidate uses `LLM_PROXY_URL=http://llm-proxy:11500` (by name on `gate-net`,
  no `extra_hosts`); generator + embed tags only, no `keep_alive`, no
  `/api/pull`/`/api/delete`). The URL is always env-only (`endpoint_env`), so the executor swaps it without
  code changes. **Dev stack on the VM (Y1.4, DEV11-10):** the tunnel's `172.17.0.1` bind is firewalled to the `proxy-egress` subnet (D242), so the dev
  service `rag-demo-dev` in `infra/gpu/compose.rag-demo.yml` (profiles `gpu` + `dev`) runs with
  `network_mode: host`, listens on `127.0.0.1:18000` and uses `OLLAMA_GPU0_URL=http://127.0.0.1:11434`, Qdrant
  `127.0.0.1:16333` and `RERANK_URL=http://127.0.0.1:18201` (dev ports); after T6.2a the dev `llm-proxy`
  (`http://127.0.0.1:21500`, docker.md §3) may be used instead. The isolated variant (internal network, no ports)
  is defined by T6.2a's `compose.executor.yml`, not here. The judge lane (`OLLAMA_GPU1_URL`) is never
  configured in rag-demo (one Ollama server since ADR-0018; `llm-proxy` blocks every judge tag).
- `RagConfig.generator` / `embed` gain `catalogue_id` (format `ollama/<tag>`, Y3.3 / D221; the bare tag is used
  only in the Ollama request body; must exist in `infra/gpu/models.yaml` when the profile is `gpu`; validated at startup with a clear error) and `endpoint_env` (URL from env, set by
  compose / the executor from `infra/gpu/endpoints.yaml`).
- `/v1/info.models` = `{generator, generator_family, embed, rerank}` from the catalogue;
  `/v1/info.serving` = **static fields only** (round 9 X3.13): `{engine: "ollama" | "llama.cpp", engine_version, quantization, gpu, model_sha256}`
  (`engine_version` (the Ollama version) and `gpu` (`A40`) from env `SERVING_ENGINE_VERSION`, `SERVING_GPU`; tier 1 keeps `gpu = "cpu:<cpu model>"`, T1.13; `quantization` from the catalogue (`Q8_0`); `model_sha256` = the Ollama manifest digest from the catalogue `digest`). It is part of the
  target fingerprint, so a serving change invalidates cached answers. Runtime counters (`think_stripped`, `truncated_chunks`, `requests`) stay in `/v1/health.stats` (T1.13) and never enter `serving`, so repeated runs hit the target cache (T6.1).
- **Profiles (round 9 X3.15):** `configs/rag.yaml` stays the tier-1 CPU profile (≤ 2B llama.cpp, `top_k: 4`, `reranker: off`); **tier 2 uses `configs/rag.gpu.yaml`**, which the executor reads from the PR (T6.2a) and which T6.5's reranker demo edits. Both stay gated paths (`rag*.yaml`).
