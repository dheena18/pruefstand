## Goal

**One** Ollama server on `cairo-s101lp` serves both A40s on `127.0.0.1:11434` (ADR-0018): the server that already
runs there is reused when healthy; only if none runs is one started **detached with `setsid nohup`** from a
generated `cluster.env` (`CUDA_VISIBLE_DEVICES=0,1`, `OLLAMA_MAX_LOADED_MODELS=3`, `OLLAMA_NUM_PARALLEL=4`,
`OLLAMA_KEEP_ALIVE=24h`), never a second one. It holds generator + `bge-m3` and the PR judge (or the gemma
nightly judge at night); Ollama places them on the cards and the health check verifies placement through
`/api/ps`. All models live in `ollama-models/` on the NAS. The VM checks, switches (API loads/unloads only)
and pulls models over SSH and the `autossh` tunnel, under the single VM GPU lock
`/var/lib/pruefstand/gpu.lock`. Every Ollama call uses the **native** API with the catalogue's fixed
per-model `options`. A CPU reranker service and Qdrant run on the VM. A machine-readable catalogue
(`infra/gpu/models.yaml`) and endpoint map (`infra/gpu/endpoints.yaml`) describe it for later tasks. Model
choices are **provisional**; T3.1b pins them.

## Context

- **No Docker, no vLLM, no TEI on the cluster; nothing stored there** except under the NAS mount (local
  disk is full). Cluster scripts live in `infra/cluster/` in the repo and are copied by the VM into NAS
  `bin/` (`$PRUEFSTAND_DATA_ROOT/bin` on the VM = `$CLUSTER_NAS_ROOT/bin` on the cluster); they run as
  `ssh "$CLUSTER_SSH_HOST" bash "$CLUSTER_NAS_ROOT/bin/<script>.sh"`.
- **Reuse, else one detached start (ADR-0018, Y5.4, D228).** `start-ollama.sh` (no arguments) first checks
  `curl -sf http://127.0.0.1:11434/api/tags` on the cluster: if a server answers (the pre-existing one, setup log
  §1/§3), it starts nothing and exits 0. Only if none answers does it start **one** server with
  `setsid nohup env … ollama serve >"$NAS/run/ollama.log" 2>&1 </dev/null & echo $! >"$NAS/run/ollama.pid"`
  (never `tmux`, never a second server), so it survives the end of the SSH session regardless of
  `KillUserProcesses` (T0.6 checked this). PID file and log live under **`$NAS/run/`** only (round 12 A12-M3).
  `status.sh` finds the server by the pid file **or** `pgrep -u "$USER" -f 'ollama serve'` plus the listener on
  `:11434`, reads its environment from `/proc/<pid>/environ` and reports every `OLLAMA_*`/`CUDA_VISIBLE_DEVICES`
  value that differs from `cluster.env` as WARN (restarting the pre-existing server is an owner step, runbook §2a).
  `stop-ollama.sh` acts only on a server whose pid file the scripts wrote; before acting on a pid both scripts
  check that `/proc/<pid>/cmdline` is `ollama serve` and that `:11434` is listening: a stale pid file (after a
  cluster reboot the pid may belong to another process) → removed and reported, **never killed**.
- **`cluster.env` (Y6.3, D231; DEV11-08).** The single source of the server settings is
  `infra/cluster/cluster.env.template` (committed, no secrets). `deploy-cluster-bin.sh` renders it to NAS
  `bin/cluster.env` together with the scripts and lists it in `SHA256SUMS` (`health.sh` exit 14 covers it).
  `start-ollama.sh` derives the NAS root from its own path (`NAS="$(cd "$(dirname "$0")/.." && pwd)"`; the
  VM's environment is not forwarded over SSH), sources `"$NAS/bin/cluster.env"` and refuses to start without it.
  Template contents (values from gpu-cluster.md §2.1/§4 and ADR-0018; **verify** each name against the pinned Ollama
  version): `OLLAMA_NUM_PARALLEL=4` (server-wide), `OLLAMA_MAX_LOADED_MODELS=3` (generator + embeddings + one
  judge), `OLLAMA_KEEP_ALIVE=24h`, `OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KV_CACHE_TYPE=f16`, `OLLAMA_NOPRUNE=1`
  (AI11-14d), `OLLAMA_BIN` (default `ollama`). No per-GPU keys, no server-side default context (the catalogue
  `num_ctx` on every request is the only control), no `OLLAMA_SCHED_SPREAD`.
- **Z7:** when it starts the server, `start-ollama.sh` exports `OLLAMA_MODELS=$NAS/ollama-models`,
  `OLLAMA_HOST=127.0.0.1:11434` and `CUDA_VISIBLE_DEVICES=0,1` before `ollama serve` (fixed in the script, never in
  the template); otherwise Ollama falls back to `~/.ollama` on the full local disk. It refuses if the NAS path is
  not mounted.
- **Generator facts (setup log §3, ADR-0018):** `/api/tags` lists `qwen3.8:27b-q8_0`, Ollama family `qwen35`,
  27.3 B, `Q8_0`, digest `8f5fb6b71ea00052cbe8545738c55ce61112c4e571cb60ca4dad00b131766039`, native context 262 144,
  capabilities `completion, tools, thinking, vision`. The catalogue entry uses this tag and digest (provisional
  until T3.1b), `family: qwen`; `core/data/model_families.yaml` gets a row mapping the tag / Ollama family `qwen35`
  to `qwen` (T1.2's table; own hunk); because the capability `thinking` is present, the entry carries
  `think: false` and every request sends `"think": false` (D95).
- **One-time migration (Z7, AI11-08):** if T0.6 C4 found that the running server does not use the NAS
  `ollama-models/` (e.g. Ollama's default store), move the model into `ollama-models/` once (copy the `blobs/` + `manifests/` entries of that tag, verify the digest)
  or re-pull it with `OLLAMA_MODELS` set; record which. If T0.6 found the tag **local-only** (not on the
  registry), also copy blobs + manifest to `$NAS/backups/models/` (digest-checked), since it cannot be re-pulled.
  and switch the server to the NAS store (the owner restarts the pre-existing server with `cluster.env`, runbook
  §2a). A port held by a system `ollama.service` or another user (T0.6 `port-11434` WARN) is resolved as T0.6
  recorded (admin stops it, or another port via `.env` + docker.md §3).
- **Native API only (Y3.1, D219).** Load = `POST /api/generate {"model": <tag>, "keep_alive": <catalogue>, "options": <catalogue options>}`
  (empty prompt), unload = the same with `"keep_alive": 0`; chat = `/api/chat`, embeddings = `/api/embed`;
  resident models = `GET /api/ps`. Never `/v1/*`. **Preload uses exactly the catalogue `options` of the model**
  (Y3.2, D220), so the first real request does not trigger a reload.
- **Model ids (Y3.3, D221):** catalogue `id` = `ollama/<tag>` (also `endpoints.yaml.model_id` and every
  config); the bare `<tag>` appears only in Ollama API bodies and in the `tag` field.
- Modes (gpu-cluster.md §2; ADR-0018: API loads/unloads only, never a server start/stop/restart): `day`
  (generator + `bge-m3` + PR judge), `night` (unload the PR judge, load gemma), `datagen` (unload all, load
  llama 70B, which Ollama splits over both cards).
- **Placement check (ADR-0018).** Ollama places models; `health.sh` requires `size_vram == size` for every
  resident model (`/api/ps`, exit 15) and, outside datagen, that no model spans both cards (exit 15). `status.sh`
  reports the card(s) per model by joining `nvidia-smi --query-compute-apps=pid,gpu_uuid,used_memory --format=csv`
  with each model's Ollama runner process (its `--model` blob path ↔ the manifest layers of the tag); **verify**
  this join on the pinned Ollama version and fall back to the server log's offload lines if it does not hold.
  Generator/judge separation is by model (the `llm-proxy` allow-list, T6.2a), never by port.
- **GPU lock (X2.1, Y1.1/Y1.2, D211/D212, binding):** one host-wide lock file `/var/lib/pruefstand/gpu.lock`
  (created by T0.7), taken once per job by the caller: the orchestrator (user `pruefstand`, T6.2a) or, for the
  owner and agents, the wrapper **`pruefstand-lock <cmd>`** (T0.7) used by every lock-taking `mk/gpu.mk`
  target. The VM scripts `infra/gpu/switch-mode.sh`, `infra/gpu/health.sh`, `infra/gpu/fetch-model.sh`
  **never take the lock** (no `flock` call) and exit 2 with "run under the GPU lock: PRUEFSTAND_LOCK_HELD=1 not
  set" unless `PRUEFSTAND_LOCK_HELD=1`. `deploy-cluster-bin.sh` needs no lock (interfaces §1.5). Tests point the
  lock dir at a temp dir with `PRUEFSTAND_LOCK_DIR` (default `/var/lib/pruefstand`; production never sets it).
- **`MAINTENANCE` (Y1.2, Y6.2, D212, D230):** the file `/var/lib/pruefstand/MAINTENANCE` (never an env var,
  never under a home directory). `switch-mode.sh datagen` **creates it itself**; `switch-mode.sh day` removes it
  (the only way out of datagen); while it exists only `datagen` and `day` are accepted by `switch-mode.sh`
  (`night` → exit 3 "MAINTENANCE set: only datagen allowed"); `health.sh` checks the mode recorded in it
  (`datagen`). No `--force` flag and no `FORCE=1` in `mk/gpu.mk` are needed (DEV11-06 is resolved by this rule).
  The orchestrator skips gated work while the file exists (T6.2a).
- **Cluster identity (Y1.1, D211).** Only user `pruefstand` holds the cluster key. The VM scripts reach the
  cluster through one helper `infra/gpu/lib/cluster_ssh.sh`: as `pruefstand` it runs `ssh "$CLUSTER_SSH_HOST" …`
  directly; as any other user it runs `sudo -n -u pruefstand /usr/local/bin/pruefstand-cluster <op> <args>`.
  `infra/gpu/pruefstand-cluster` is a small trusted forced-command wrapper (installed by the owner with sudo,
  plus one sudoers line `%pruefstand ALL=(pruefstand) NOPASSWD: /usr/local/bin/pruefstand-cluster`) that accepts
  only `start-ollama`, `stop-ollama`, `status`, `pull <tag>`, `rm <tag>`, `show <tag>` (no mode or GPU arguments, ADR-0018)
  (tags matched by `^[a-z0-9._:/-]+$`) and runs the fixed `bin/` scripts or `ollama` with the NAS store; anything
  else → exit 64. **Mutating ops need the GPU lock (round 12 A12-M5):** `start-ollama`, `stop-ollama`, `pull` and
  `rm` run only when the caller holds `/var/lib/pruefstand/gpu.lock`: the sudoers line keeps the variable
  (`Defaults!/usr/local/bin/pruefstand-cluster env_keep += "PRUEFSTAND_LOCK_HELD"`), the wrapper requires
  `PRUEFSTAND_LOCK_HELD=1` **and** checks that `flock -n /var/lib/pruefstand/gpu.lock true` fails (the lock really is
  held); otherwise exit 2 "run under the GPU lock (pruefstand-lock …)". `status` and `show` stay lock-free. So an
  agent's `stop-ollama` or `rm <tag>` can no longer hit a running gate. The owner never gets a copy of the key. Ollama HTTP calls go through the tunnel on
  `127.0.0.1:11434` (both `OLLAMA_GPU0_URL` and `OLLAMA_GPU1_URL`), which every VM user can reach.
- **Which `bin/` runs (A11-M11).** Only the executor (user `pruefstand`, trusted `main` checkout) deploys NAS
  `bin/`. `deploy-cluster-bin.sh` run by any other user writes `bin-dev/` instead and `pruefstand-cluster`
  takes `--bin-dev` for those calls; `health.sh` exit 14 compares `bin/` only against the trusted checkout
  (`PRUEFSTAND_TRUSTED_CHECKOUT`, default the runner's checkout of `main`).
- **Reranker on the VM CPU (Z3, Y2.2, Y4.2):** `BAAI/bge-reranker-v2-m3` with sentence-transformers in a small
  trusted service `rerank-cpu` exposing a TEI-compatible `POST /rerank`, model weights in a VM-local volume,
  ≤ 24 GB CPU-model budget (Z7). **No auth** (D217): it is reachable only on the internal candidate network, has
  **no host port in the executor stack** and holds no secrets; the dev stack publishes `127.0.0.1:${RERANK_HOST_PORT}`
  (18201, Y1.4). Tier-2 callers send the top **10** passages truncated to 256 tokens, batched (D222); T3.1b
  measures the lane. Container port **8201**, `RERANK_URL=http://rerank-cpu:8201` (interfaces §1.5, docker.md §3,
  D247).
- **Catalogue** (gpu-cluster.md §2, interfaces §1.5): one entry per servable model with `id` (`ollama/<tag>`
  for engine `ollama`), `engine` (`ollama|cpu`), `tag` (bare), `digest` (64-hex manifest sha256; the pin),
  `quantization`, `family`, `role` (`generator|judge|nightly_judge|large|embed|rerank`), `server`
  (`gpu0|gpu1|all|vm`: the lane / URL setting, not a card or port, ADR-0018), `think` (`false` for every entry whose
  Ollama capabilities include `thinking`), **`options`** `{num_ctx, num_predict, temperature, seed, top_p}` (per-model defaults; `num_ctx`
  fixed, Y3.2; judges `num_predict: 384`, AI11-14e), **`option_bounds`** for chat entries (round 12 N2, D252:
  `{temperature: [min, max], top_p: [min, max], num_predict: [1, max]}`, every default inside its bounds; `llm-proxy`
  passes candidate sampling options within them), `num_ctx` rules (N7, AI12-08/-09): generator 8192, **judges =
  generator `num_ctx` + rubric/answer allowance ≤ 3 072 + 1 024 reserve = 12 288** (round 13, D306, SPEC §6.3: both
  the PR judge and the nightly judge; only T3.1b may lower it, and only if its VRAM measurement fails), embed entries `num_ctx == max_input_tokens` (max chunk tokens, never the
  model's 8192 default), `keep_alive` for preload, `kv_bytes_per_token` (read from `ollama show` /
  the load log in S8, AI11-07) and for Gemma `swa_window`, `license` (allowlist: no CC BY-NC / research-only), **`tokenizer: {source, sha256}`** for every chat entry (AI13-05: generator and judges; Qwen and Mistral from their HF repos, Gemma after the owner accepts its terms or extracted from the GGUF vocab with the `gguf` reader; used to count prompt tokens, never the `bge-m3` tokenizer),
  embed: `query_prefix`, `doc_prefix`, `max_input_tokens`, `provisional`. `endpoints.yaml`: name →
  `{base_url_env, model_id (= catalogue id), family, kind}` with `base_url_env` ∈ `OLLAMA_GPU0_URL`,
  `OLLAMA_GPU1_URL`, `RERANK_URL`; no host names or keys.
- The candidate's access path (`llm-proxy`, which enforces the catalogue `num_ctx`, strips `keep_alive` and load-time
  keys, and passes sampling options within `option_bounds`, round 12 N2) is T6.2a; Qdrant on the VM uses the existing root compose service with profile `gpu` and storage
  `$PRUEFSTAND_HOME/qdrant` (R9-32), published on the dev ports in the owner's stack (Y1.4).
