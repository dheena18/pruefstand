## Goal

Three real PRs on the repo prove the MVP: removing the reranker → **FAIL**, whitespace-only change →
**PASS**, tenant-filter bug → **hard FAIL**, each with a correct, single, self-updating PR comment.

## Context

Branches are created from `main` and never merged. The tenant-filter bug (M8): apply the tenant
filter after retrieval with top-k cut (post-filter) instead of inside the Qdrant prefetch — leaks only
appear when foreign chunks outrank own ones, which the planted canaries trigger. Evidence is kept in
`docs/mvp/` so it survives after the PRs are closed. The demo branches are same-repo branches, so the
normal flow applies (T6.2b, round 13 P1.2): the owner dispatches the private `gate-executor.yml` with
`pr=<N>` (browser or GitHub mobile app; there is no `run-gate` label), waits for the run, then reads the redacted
comment and the required `pruefstand/gate` status (posted by `pruefstand-bot`). A new commit has no result until
the owner dispatches again.

Round 9 (binding, `docs/planning/reviews/round9-resolution.md` X3.15, D175): tier 2 uses
`apps/rag-demo/configs/rag.gpu.yaml`, which the executor reads from the PR. `rag.yaml` is the tier-1 CPU profile
and already has `reranker: off`, so editing it would demonstrate nothing in tier 2. The reranker demo therefore
edits **`rag.gpu.yaml`**. All three demo branches touch a gated path (`apps/rag-demo/**`), so none of them gets
"not gated" from `gate-router.yml`.

Round 8 (binding, `docs/planning/reviews/round8-resolution.md`):
- These demos run in **tier 2** on the A40 executor (`core` split). The reranker demo is a *statistical*
  bug-switch scenario, which belongs to tier 2 (W1.5, D98); tier 1 only proves the deterministic hard fail.
- **Precondition:** `baseline-promote` has produced a `main` baseline for the current `eval_fingerprint`.
  Otherwise every demo PR gets `failure` "no baseline for <fp>; run baseline-promote" (W2.4, D103) — check
  the private `baselines/index.json` before dispatching.
- The comment shows the MDE per gated metric (W3.6); metrics with < 30 applicable clusters and judged metrics
  of an uncalibrated/degraded/drifted judge are informational (`informational_reason` shown), never FAIL.
