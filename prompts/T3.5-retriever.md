## Goal

`QdrantRetriever.retrieve(tenant_id, query, top_k)` runs one Qdrant Query API call with dense and
sparse **prefetch, each carrying the tenant filter** `tenant_id ∈ {tenant, "shared_public"}`, fuses
with RRF, optionally reranks (`bge-reranker-v2-m3` on the **VM CPU**, service `rerank-cpu` at `RERANK_URL`), and returns `top_k` hits. The tenant
filter is built in exactly one function and its presence in every prefetch is unit-testable. The same retriever
backs the new target endpoint **`POST /v1/retrieve`** (R11 Y2.3, D218): chunks only, **no generator call**, used by
the runner for every `robust_pr` case (D222).

## Context

**This task extends rag-demo v0 (T1.13)**: the module already exists in minimal form and is used by tier-1 CI. Upgrade it in place, keep every bug switch from T1.13 working (their tests must stay green) and keep the CPU `live` profile working. No new parallel module, no stub/simulated classes (ADR-0008); tests use the real services (Testcontainers Qdrant, TEI CPU, llama.cpp from compose `live`) or cassettes recorded from them.

- Single choke point: `tenant_filter(tenant_id) -> models.Filter` and
  `build_query(tenant_id, dense, sparse, cfg) -> QueryRequest`. `retrieve` must only call Qdrant via
  `build_query`. A test inspects the built request object: **every** `prefetch` entry has the
  filter, and the top-level query has it too (defence in depth).
- Mutations this design must make easy to inject **and** detect (T7.1a/T7.1b implement them as patches):
  - **M8** "tenant filter applied after retrieval with top-k cut": query without filter, then
    Python-side filter, then cut → can leak or under-fill. Detected by the request-inspection test
    and by integration test "foreign canary chunk ranks first without filter".
  - **M9** "tenant filter missing for `shared_public` merge": e.g. a second unfiltered prefetch for
    shared docs, or `should` instead of `must`. Detected by the per-prefetch test and by a Hypothesis
    test over random tenants/queries against the fixture corpus.
  - M1 remove reranker (`reranker: off` in `configs/rag.gpu.yaml`, the tier-2 profile the executor reads, X3.15), M3 weaker embedding, M10 `top_k` 8→3 are pure config. The `RagConfig` default stays `reranker: off` (interfaces §16, D9-26); only `rag.gpu.yaml` and `configs/bugs/gpu/*.yaml` set `on` (S7).
- Prefetch limits: dense `prefetch_k` (default 50), sparse `prefetch_k` (default 50); RRF k=60;
  rerank the first `rerank.top_n` fused hits (tier 2: **10**, passages truncated to **256 tokens** client-side and
  sent as **one batched** `POST /rerank` per query, R11 Y4.2 / D222), then cut to `top_k` (default 8). If T3.1b
  measured the reranker lane > 20 min per PR run, the `robust_pr` path runs with the reranker off: round 12
  DEV12-09 (interfaces §16, pre-approved): **`rerank.on_retrieve: bool = True`**; `false` makes `POST /v1/retrieve`
  skip the reranker (set in `rag.gpu.yaml` only when T3.1b records the decision; part of `config_hash`, so of the
  target fingerprint; documented as first-stage robustness). `/v1/query` is never affected, so `core` keeps the
  reranker. There is no request field and no executor override for this (AI12-07 closed).
- **`POST /v1/retrieve` (R11 Y2.3, D218; interfaces §1.1).** Request = the `/v1/query` request
  (`{tenant_id, question, top_k, request_id}`); response = `{"chunks": [...]}` with exactly the chunk shape and
  order `/v1/query` would return when `rerank.on_retrieve` is true (tenant filter + reranker as configured; with
  `on_retrieve: false` the fused order cut to `top_k`; `used_in_prompt` absent), **no `answer`,
  no generator call** (a test asserts the generator is never constructed or called on this path). Same input
  validation, tenant checks and post-condition guard as `/v1/query`; `/v1/health.stats.requests` counts it. It is a
  backward-compatible API v1 addition: update the FastAPI app, regenerate `schemas/target-api-v1.openapi.yaml`
  (`make schemas`) and record `packages/pruefstand/tests/contract/examples/retrieve_ok.json` from the real app
  (T1.3's adapter test replays it).
- `Hit` (from `rag_demo.models`, T1.13): `chunk_id, doc_id, tenant_id, text, score, rank, citation_key, section, lang`.
- **Reranker placement (round-8 W3.10, binding):** tier 1 (`live` profile, CPU) has **no reranker** (`reranker: off`, `IdentityReranker`; budget, W1.2). Tier 2 uses `CrossEncoderReranker` via the TEI-compatible `POST /rerank` of the VM service **`rerank-cpu`** (T3.1a; sentence-transformers on the VM CPU, round 10 Z3; URL from env `RERANK_URL`, never a GPU and no TEI on the cluster) with `BAAI/bge-reranker-v2-m3` (Apache-2.0, **verify** on the pinning day), top **10** (256-token passages, batched) → `top_k`, pinned in `infra/gpu/models.yaml` (`engine: cpu`, `server: vm`). **No auth** (R11 Y2.2, D217): the client sends no `Authorization` header and reads no key; `rerank-cpu` is reachable only on the internal candidate network (dev stack: `127.0.0.1:18201`). CPU latency for 10 pairs is part of the PR budget as the retrieval lane (T3.1b measures it). `reranker: off` in a tier-2 config is mutation M1 (statistical, T6.5). No CC BY-NC model in any default profile (`test_catalogue.py`, T3.1a, checks a `license` field).

## Interfaces (must match `interfaces.md` exactly)

```python
class Retriever:       def retrieve(self, tenant_id: str, query: str, top_k: int) -> list[Hit]
                       # Qdrant Query API: prefetch dense + sparse, both with filter tenant_id ∈ {tenant, "shared_public"},
                       # RRF fusion, then optional rerank. The filter is INSIDE every prefetch (never post-filter).
class Reranker(Protocol):      def rerank(self, query: str, hits: list[Hit], top_n: int) -> list[Hit]
```
```text
POST /v1/retrieve   request : {"tenant_id": str, "question": str, "top_k": int | null, "request_id": str}
                    response: {"chunks": [{"chunk_id", "doc_id", "tenant_id", "text", "score", "rank"}]}   # no answer, no generation (D218)
```
