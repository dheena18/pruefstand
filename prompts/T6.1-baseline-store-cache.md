## Goal

Baselines are stored and fetched by `(eval_fingerprint, ref)` from a local directory or a git branch,
with bounded retention. Caches are split by trust domain. A sanitised copy of any run can
be exported for public use and pushed to the public dashboard-data repo. All runs are queryable with DuckDB.

## Context

- **Baselines (round 9 X2.7 + round 10 D209, binding; supersedes the D145 layout):** the run **files** live in the
  **data root**, a plain directory on the VM disk (ADR-0019), under `BaselineStoreConfig.data_root` (default **`$PRUEFSTAND_DATA_ROOT/baselines`**
  = `/mnt/pruefstand/baselines`; when `PRUEFSTAND_DATA_ROOT` is unset (local dev, CI) `$PRUEFSTAND_HOME/baselines`):
  `<data_root>/<eval_fingerprint>/<ref>/{run.json, results.parquet, responses.jsonl.zst, manifest.json}` (the
  current baseline) plus one `<data_root>/<eval_fingerprint>/history/<run_id>/{run.json, results.parquet,
  manifest.json}` per promotion (last 20 kept; `responses.jsonl.zst` only for the current `<ref>/`, never in
  `history/`), and they are in the `age`-encrypted weekly backup (X2.6, T6.2b). The **private** executor repo
  `dheena18/pruefstand-gate`, branch `baselines` (protected, no force-push), keeps **only** the small
  `baselines/index.json` (per `(fp, ref)`: ordered run ids + the manifest sha256 of each, newest = current), so the
  repo no longer grows with every promotion. `ref ∈ {"main", "nightly-b0", "nightly-b1", "nightly-b2", "release-b0", "release-b1", "release-b2"}`
  (ADR-0004, data-model.md §7; round 12 N1.4: **`nightly-b<k>`** = the latest promoted `main` nightly of block *k*;
  round 13 D305/D321: **`release-b<k>`** = the block-*k* projection of the release run; PR runs compare with ref
  `main`; any other ref, incl. `release`, → `StoreError`). `get()` reads
  `index.json` from git, then verifies the files on disk against the manifest sha256 (integrity against partial
  writes and disk loss, not authenticity); a mismatch or a missing file raises `StoreError`. Plain files, **no
  signatures**: write access to the private repo and the VM service user **`pruefstand`** (round 11 Y1.1, D211; the only identity that writes the data-root `baselines/`; the owner login user and coding agents never write there) is the trust boundary (D63).
- **Data root rules (gpu-cluster.md §9, binding):** one writer (`baseline-promote.yml` on the VM as user `pruefstand`, under `/var/lib/pruefstand/gpu.lock`, D211); write
  each run dir as `<name>.partial` (temp dir on the same file system), `fsync`, then one `rename` to the final name;
  readers ignore `*.partial`; `index.json` in git is updated **only after** the rename succeeded; history dirs are
  immutable. No locks, DuckDB or caches in the data root: the `RunIndex` DuckDB file, the target/LLM caches and in-progress
  run dirs stay on the VM disk (`$PRUEFSTAND_HOME`; for the executor `/home/pruefstand/pruefstand`, D211). A missing `data_root` (no `.pruefstand-data-root`
  sentinel in its parent) → `StoreError` with a clear message, never an empty store (so a missing data root can never
  look like "no baseline"). Move whole dirs with one copy.
- **Retention (round 8 W2.11, round 9 R9-14, binding):** keep the **last 20 baselines per fingerprint** (per ref);
  `pruefstand baseline prune --keep 20` deletes older `<data_root>/<fp>/history/<run_id>/` directories and
  fingerprints unused for 90 days on disk and updates `index.json` in one normal commit (no force-push). It is run
  by the **monthly** `baseline-prune` step of `baseline-promote.yml` (first poll after 00:00 UTC on day 1, T6.2b),
  so baselines are written only by `baseline-promote.yml`. Private run artefacts are kept **14 days** (T6.2b
  `retention-days: 14`; VM run dirs under `$PRUEFSTAND_HOME/runs/` rotated by `nightly.yml` `runs-prune`). `GitBranchBaselineStore` reads
  `index.json` with `git clone --depth 1 --filter=blob:none --single-branch -b baselines` (the branch holds one
  small file).
- **Nightly baselines and drift (round 12 N1.4, binding).** `RunManifest.block` and `judged_subset` are part of
  `eval_fingerprint` (T1.1), so each block has its own fingerprint.
  - `baseline promote --run <nightly run> --ref nightly-b<k>` refuses a run whose `RunManifest.block != k`
    (usage error, exit 2, store unchanged); `--ref main` refuses a run with `block is not None` (exit 2).
    **Release anchor (round 13 D305/D321, binding):** the refs `release-b0..b2` are written only from the **release
    run** (the newest `v*` tag's image on all of `full`: `block=None`, `stratum="all"`; T6.2b runs it alone on a
    night until the three refs exist for the current fingerprint). `baseline promote --run <release run> --ref
    release-b<k>` requires `block is None` and `stratum == "all"` (else exit 2) and writes the **block-*k*
    projection**: the records and values of the refusal stratum + block *k*, `RunManifest.block = k`, and the
    fingerprint recomputed via `core.fingerprint` with `block=k` (never by hand), i.e. exactly the fingerprint of the
    nightly of block *k*. `baseline-promote.yml` calls it for k = 0, 1, 2.
  - `gate --from-store --ref nightly-b<k>` (k = the candidate's `block`) fetches `get(candidate_fp, "nightly-b<k>")`;
    a mismatch between `--ref nightly-b<k>` and the candidate's block → `GateInputError` (exit 3).
  - **Drift vs `release-b<k>`:** `gate --from-store --ref release-b<k>` on a candidate with `block = k` fetches
    `get(candidate_fp, "release-b<k>")` (same fingerprint; `--ref release-b<j>` with j ≠ k → `GateInputError`); there is
    no cross-fingerprint lookup and no restriction at gate time (the projection happened at promotion); every
    fingerprint mismatch → `GateInputError`. No `GateReport` field is added.
- **Cache trust domains:** `LayeredKVCache(base, overlay)` reads `overlay` then `base`, and
  writes only to `overlay`.
  - PR jobs: the base is main's shared cache opened read-only, and the overlay is a per-job temp
    directory that is deleted after the job.
  - main/nightly jobs: one writable shared cache.
  - The mode comes from env `PRUEFSTAND_CACHE_MODE=shared|overlay` (default `overlay`).
- **Fingerprints:** `core/fingerprint.py` already includes `models` and `serving` in
  `target_fingerprint` (T1.1, interfaces §17); this task only adds tests for cache invalidation.
- **Sanitised export:** `sanitise_run` returns a copy for public use:
  - chunk `text` removed (ids, doc ids, scores kept);
  - every canary token and `forbidden_strings` value masked as `‹redacted›` in answers;
  - every case built from canaries dropped: a case whose `forbidden_strings` contain the token or fact of
    any canary in `canaries` is removed (with its records and values). `CanaryRegistry` has no
    public/held-out flag, so callers pass public + held-out canaries merged and all canary-probe cases are
    dropped (public probes are in the published dataset anyway); this also keeps `forbidden_strings` out
    of the export;
  - `responses.jsonl` rewritten.
  - **Registry source** (the CLI has no registry flag): `store/canary_source.py`
    `load_canary_registry() -> CanaryRegistry` merges every `corpus/*/canaries.public.json` (T1.13 slice),
    `datasets/canaries/*/canaries.json` (T2.6, if present) and, when `PRUEFSTAND_HELDOUT_DIR` is set,
    `$PRUEFSTAND_HELDOUT_DIR/canaries_heldout.json`. No registry file found → `StoreError` (never export
    unsanitised). `export-public` (and T8.1's `export-dashboard`) use it. It runs only in the executor's trusted
    steps; the held-out registry is never mounted into or reachable by a candidate container (round 9 X2.5).
- **No baseline in the store (round 8 W2.4, binding):** `pruefstand gate --from-store` when `get()` returns
  `None` writes `gate.json` with `status=INSUFFICIENT_DATA`, `GateReport.no_baseline = true`,
  `baseline_run_id = None` (round 9 X5.5), no decisions, and the message "no baseline for
  <eval_fingerprint>; run baseline-promote", and **exits 0** (interfaces §15; not `StoreError`/exit 3). The
  CLI never decides the commit state: on a **gated PR** the executor (T6.2a S8) calls
  `set_check(sha, status, summary, no_baseline=report.no_baseline)`, whose single mapping table (interfaces §10,
  round 9 X4.6) turns `no_baseline = true` into `pruefstand/gate` = **`failure`** with that message (D103; never a
  pass, never an ad-hoc main run). For
  `main` / nightly runs this is simply the first run under a fingerprint, which becomes the baseline via
  baseline-promote (T6.2b's first nightly relies on it).
- **Dashboard data (round 8 W2.9, binding):** no token of the private repo ever lives in the public repo.
  The executor pushes the **sanitised** export (+ `manifest.json` with sha256 per file) to the separate
  **public** repo `dheena18/pruefstand-dashboard-data` with a fine-grained PAT scoped to **that repo
  only** (`contents: write`), stored only in the private repo (env `DASHBOARD_DATA_PAT`). `store/dashboard_repo.py`
  `push_dashboard_data(src: Path, repo: str, *, token_env: str = "DASHBOARD_DATA_PAT", extra: Mapping[str, bytes] | None = None) -> str`
  clones it shallow, adds the new run's files, writes `extra` files and then (**round 13 P5.1, binding**) **rewrites
  the whole published tree from the index**: it rebuilds `runs/index.json` from every `runs/*/run.json` in the data
  repo (never from the VM run dirs), keeps the newest **200** runs (`runs/<id>/` beyond them deleted) and the case
  shards + `report.html` only for the newest **20** (`cases/<id>/` and older `report.html` deleted), rewrites
  `manifest.json` (sha256 per remaining file), commits and pushes to `main`, so old data is pruned on every push.
  The two caps (`MAX_INDEX_RUNS = 200`, `MAX_CASE_RUNS = 20`, D259) are imported from **`core.models.dashboard`**
  (round 13, binding), so T8.1's export and verifier and this task's size check use the same values; never redefine
  them here. The heartbeat
  does **not** go through it (round 9 R9-21): `push_heartbeat(repo, payload, *, token_env="DASHBOARD_DATA_PAT")`
  writes `heartbeat.json` as a single force-pushed commit on branch `heartbeat` of the same repo (no data-repo
  `main` growth; `executor-health.yml` reads it there); T6.2a calls it every **15 min** during long jobs and lock
  waits and at the end of every job (round 11 Y5.1, D225), so the payload values are strings
  (`ts`, `last_job`, `tunnel_ok`, `ollama_gpu0_ok`, `ollama_gpu1_ok`, `data_root_ok`, `disk_free_gb`,
  `last_nightly_result`, `laptop_backup_age_days`; A11-07, Y5.5; round 12 N4.3 / A12-M2 add `last_nightly_status`
  (round 13 A13-M3, one vocabulary: `ok` \| `failed` \| `aborted: window_exceeded` \| `skipped: maintenance` \|
  `skipped: runner busy` \| `skipped: preflight <reason>`), `last_nightly_at` (ISO time of the last **completed**
  nightly, `ok` or `failed`; a skip or abort leaves it unchanged), `<field>_false_since` (ISO time or empty string)
  for each boolean health field (`tunnel_ok`, `ollama_gpu0_ok`, `ollama_gpu1_ok`, `data_root_ok`), `maintenance`
  (A13-M4: `/var/lib/pruefstand/MAINTENANCE` present) and `drift_no_release_baseline` (A13-M5); field names as in ci-cd.md §1.2) and the function stays cheap (one shallow fetch + one
  force-push, < 10 s). The token reaches git only through `GIT_ASKPASS` / a credential helper env, never on
  argv, in a URL or a log. It refuses a `src` that was not produced by `sanitise_run` (marker in its
  manifest) or that contains `CANARY-`. T8.1/T8.5 read that repo anonymously.
- **What may become a baseline (round 11 Y4.4/Y5.2, D224/D226):** `put()` and `baseline promote` refuse
  (`StoreError`, exit 1, store unchanged) a run with `complete=False` (this includes every
  `stop_reason="aborted"` run with `infra_error`) and a run with `RunManifest.judge_fallback = True` (message
  "judge fallback run (<judge id>): not promoted; judged metrics are never compared across judges"). **Round 13
  AI13-08 / D321:** the same refusal for `judge_drift = True`, `judge_degraded = True` or a judged metric whose
  `informational_reason` is `judge_truncated` (message names the flag), so a judge flagged tonight never writes a
  baseline; flagged runs are **never promoted to any ref** (no deterministic-only promotion), including
  `release-b<k>`. The previous
  baseline stays current; the next normal run promotes as usual.
- **Git store:** `GitBranchBaselineStore` uses the `git` CLI via `subprocess.run([...], check=True)`
  with list args on a temp worktree. It never uses `shell=True` and never embeds tokens in URLs or logs.
