## Goal

Branch protection, environments, secrets, GitHub Apps and external accounts exist, so that AI sessions
can open PRs that are checked, reviewed and later gated on the A40 cluster through the private
executor repo.

## Context

These steps need your accounts; an AI session can't do them. Never paste tokens or private keys into a
chat. Put them only where `docs/ops/secrets.md` says (GitHub repo/environment secrets; local `.env` only for the local
`PRUEFSTAND_GH_MODELS_TOKEN` (never named `GITHUB_TOKEN`, D333) and `HF_TOKEN`). App keys and PATs never go into a `.env`.

**Required checks rule:** only checks that exist **and** report on every PR may be required. A required
check that is path-filtered, label-gated or not created yet keeps every PR pending forever. Each
workflow ends in one aggregator job (T0.2), so the required names are short and stable:

**Solo maintainer:** PRs are required but **0 approvals** are required (you cannot approve your own PR).
Review comes from the `_review.md` session and a second-family reviewer (`gh models run`, or Copilot
code review if you have a Copilot subscription; Copilot is not part of GitHub Pro).

## Subtasks

Now (right after T0.2 is merged):

- [ ] S1 Settings → General: **squash merge only**, auto-delete head branches, "Always suggest updating PR branches".
- [ ] S2 Settings → Rules → new ruleset for `main`:
  - require a PR, **0 required approvals**, require conversation resolution, require linear history (**not** "require branches to be up to date": it would force a new owner dispatch and a serial A40 run for every open gated PR after each merge; post-merge baseline-promote and nightly catch interactions; A8-09, decision line)
  - block force pushes and deletion; **bypass list = role Repository admin (the owner) only**, mode "pull requests only", for cluster outages (round-8 W2.7). Every bypass is logged in `docs/ops/bypass-log.md` (date, PR, reason, nightly re-run after recovery)
  - required status checks: `ci / check`, `security / scan` (the "now" rows of the table above)
- [ ] S3 Settings → Actions → General:
  - "Require approval for **all** outside collaborators" for fork PR workflows
  - default workflow permissions **read-only**
  - disallow Actions from creating or approving PRs
  - **do not add any self-hosted runner to this repo**
- [ ] S4 Settings → Code security: Dependabot alerts + security updates, secret scanning + push protection, private vulnerability reporting.
- [ ] S5 Labels: `task`, `interface-change`, `human-needed`, `blocked`. There is **no** `run-gate` label (round 13 P1.2): tier 2 for a PR starts only when you dispatch `gate-executor.yml` in the private repo (input `pr`) from the browser or the GitHub mobile app.
- [ ] S6 Settings → Pages → Source: **GitHub Actions** (used by T0.4 `docs.yml` deploy).

Add these to the required checks when the task that creates them is merged:

- [ ] S7 Add each later row of the required-checks table when its task is merged. For `pruefstand/gate`, set the expected source to the App **`pruefstand-bot`** (round 13 P1.1). Both writers post with that App: `gate-router.yml` ("not gated" only, App token from environment `gate-router`) and the executor. A branch workflow that posts the context with `GITHUB_TOKEN` (possible because the VM token has Workflows: write) does not satisfy the pinned check. `gate-router.yml` is the only `pull_request_target` workflow, runs no PR code (no checkout) and never posts on a PR that touches a gated path.
- [ ] S7a (with T6.2b) Public repo → Settings → Environments → new environment **`gate-router`**: deployment branches **`main` only** (a `pull_request_target` run executes in the context of `main`), no required reviewer; secrets `BOT_APP_ID`, `BOT_APP_KEY` (the same `pruefstand-bot` App as the executor). The T0.2 workflow guard allows `environment: gate-router` only in `gate-router.yml`.

Later (before the listed task):

- [ ] S8 (T4.7b) Hugging Face account `<HF_USER>`; fine-grained write token for `<HF_USER>/pruefstand-de`, stored as secret `HF_TOKEN` in the environment `huggingface` (required reviewer = you).
- [ ] S9 (T5.1) GitHub Models access check (`gh models list`). No paid API keys (D86, free providers only). Public workflows reach GitHub Models only through the Actions `GITHUB_TOKEN` with `models: read`, passed to the code as `PRUEFSTAND_GH_MODELS_TOKEN: ${{ github.token }}` (D333) (`live-e2e.yml`, `cassettes.yml` only; `action-selftest.yml` runs with judged metrics off, R9-15); no other model credential is stored anywhere in the public repo.
- [ ] S10 (T6.2a, after T0.6 says "go") Create the **private** repo `dheena18/pruefstand-gate` (the gate executor). Register the self-hosted runner **on the VM `pruefstand-exec`** (T0.7; it reaches the A40 Ollama servers only through the tunnels; nothing is installed on the cluster) **only there** (label `a40`) by hand **once**, with a registration token from that repo's Settings → Actions → Runners (no App for this). The runner is **persistent, not ephemeral** (round-8 W2.1): it runs as the **system** unit `pruefstand-runner.service` with `User=pruefstand` (the single service identity created in T0.7; round 11 Y1.1 / D211; no mount dependency, ADR-0019 / D331) and has `ACTIONS_RUNNER_HOOK_JOB_STARTED` / `ACTIONS_RUNNER_HOOK_JOB_COMPLETED` cleanup scripts (T6.2a). No token file the owner has to refresh. Then:
  - **One** GitHub App `pruefstand-bot`, installed on the **public repo only**, permissions `statuses: write`, `pull_requests: write`, `contents: read`, `metadata: read`. The executor uses it to post the `pruefstand/gate` status and the redacted PR comment. Its private key goes into the private-repo secrets `BOT_APP_ID`, `BOT_APP_KEY` and into the public environment `gate-router` (S7a), nowhere else.
  - The private repo's own workflows use their `GITHUB_TOKEN` for everything inside the private repo (baselines branch, artefacts). Nightly results are a commit status `pruefstand/nightly` + run summary. The App opens no issue (it has no `issues: write`); the public `executor-health.yml` opens the health issues (`executor-down`, `backup-stale`, `nightly-failed`, `nightly-skipped`).
  - Private repo ruleset: protect `main` and `baselines` (no force push, no deletion).
  - (T6.2a/T8.5) Public repo `dheena18/pruefstand-dashboard-data` for the sanitised dashboard export and `heartbeat.json`; the executor pushes with a fine-grained PAT scoped to **that repo only**, stored as a private-repo secret `DASHBOARD_DATA_PAT` (round-8 W2.9). No token from the private repo ever lives in the public repo.
  - The public repo gets no gate runner and no executor secret (the executor pulls; ADR-0005). Its only gate-related secrets are the `pruefstand-bot` App id and key in environment `gate-router` (S7a), used by `gate-router.yml` for "not gated".
  - Who starts tier 2 (round 13 P1.2): only you, with a `workflow_dispatch` of `gate-executor.yml` (input `pr`) in the private repo. The VM token has no access to the private repo, so no agent can start it. For a fork PR you first mirror it with `mirror_fork_pr.sh --reviewed` (pushes `gate/pr-N`), then dispatch.

## Constraints and non-goals

- Do not grant `write` workflow permissions by default; workflows request what they need per job.
- Never register a self-hosted runner on the public repo (ADR-0005, D61).
- Do not create the private executor before T6.2a's hardening steps are written down.
